## 1. Context (배경)

사용자가 웹해킹 문제 인스턴스에 붙어서 **직접 상호작용**(로그인 폼 제출, 링크 이동, JS/AJAX
호출 등 — SQLi 같은 공격을 브라우저에서 해보는 것)을 할 수 있어야 한다.

지금은 백엔드가 경로 접두사 방식으로 프록시한다:

```
GET /api/ctf/instance/{requestId}/app/...  →  http://인스턴스host:port/...
```

문제는 화면을 **열어 보는 것(GET)** 까지만 된다는 것이다. 웹해킹 문제는 임의의 웹앱이라,
아래 경우에 상호작용이 깨진다.

* 페이지가 `<form action="/login">` 처럼 **루트 절대경로**를 쓰면, 브라우저는 그걸 프록시
  경로가 아니라 백엔드 루트(`/login`)로 보낸다. 로그인이 안 된다.
* JS가 `fetch("/api/...")` 처럼 경로를 **코드로 만들면** 그것도 백엔드 루트로 간다.
  HTML을 고쳐 경로를 바꾸는 방법(URL 재작성)으로는 JS가 만든 경로를 잡을 수 없다.
* 쿠키가 백엔드 도메인에 얹혀서, 여러 인스턴스와 백엔드가 **쿠키를 공유**해 서로 간섭한다.

즉 경로 접두사 프록시는 "앱이 자기가 루트('/')에 있다고 가정"하는 웹앱을 제대로 담지 못한다.
CTF 웹 문제는 대부분 그런 앱이다.

고려 사항:

* 어떤 웹앱이 와도 **고치지 않고** 그대로 돌아가야 한다 (문제마다 HTML을 손댈 수 없다).
* 인스턴스마다 쿠키·세션이 서로, 그리고 백엔드와 섞이면 안 된다.
* 남의 인스턴스에 접근하지 못하게 막아야 한다.
* 지금은 단일 호스트(ADR-0009)이고 인스턴스는 loopback 포트에 떠 있다.

## 2. Decision (결정)

경로 접두사 대신, **인스턴스마다 별도의 호스트 이름(서브도메인)** 으로 접근하게 한다.

```
inst-<token>.<ctf도메인>   →  라우팅 계층  →  http://127.0.0.1:<인스턴스 포트>/...
```

* 문제는 그 서브도메인의 **루트('/')에서 서비스**되므로, 절대경로·폼·JS·AJAX·쿠키가 전부
  **고칠 것 없이 그대로** 동작한다. `/login`은 그 서브도메인의 `/login`으로 간다.
* `token`은 인스턴스를 가리키는 **불투명한 값**이고, 요청한 사용자에게 묶인다. 라우팅 계층은
  Host 헤더의 token으로 인스턴스 포트를 찾고, 로그인 세션의 사용자와 token의 소유자가 같은지
  확인한 뒤에만 통과시킨다.
* 쿠키는 서브도메인 호스트에 격리되어 인스턴스끼리·백엔드와 안 섞인다.
* 라우팅은 앞서 만든 프록시 전달 로직(InstanceProxy)을 재사용한다 — 다만 경로에서 인스턴스를
  찾던 것을 **Host 헤더에서** 찾도록 바꾼다.

이 결정은 **HTTP 웹 문제**에 한정한다. nc로 붙는 pwn 같은 raw TCP 문제는 서브도메인 HTTP
프록시로 담을 수 없으므로, 포트를 직접 노출하는 방식(포트 풀)으로 따로 다룬다(후속 ADR).

> **염두에 둘 것 — 포너블(pwn) 상호작용은 나중에 반드시 구현한다.**
> 지금은 브라우저에서 웹(HTTP) 문제와 상호작용하는 것만 만든다. 그러나 pwn 문제는 참가자가
> `nc host port`처럼 **TCP 소켓에 직접 붙어** 상호작용해야 한다. 이건 HTTP 프록시로는 안 되고
> 두 가지 갈래가 있다:
> * 포트를 그대로 대외 노출(포트 풀) → 참가자가 자기 터미널에서 `nc`로 붙는다.
> * 브라우저 안에 **웹 터미널**(예: xterm.js + WebSocket ↔ TCP 브리지)을 띄워 브라우저에서 붙게 한다.
>
> 어느 쪽이든 이 ADR의 서브도메인 HTTP 프록시와는 **경로가 다르다.** pwn을 붙일 때 이 문서를
> 다시 참고해서, 웹은 이 방식 / raw TCP는 별도 방식으로 나눠 설계한다.

기존 경로 접두사 프록시(`/app/**`)는 **상호작용용으로는 폐기**하고, 필요하면 간단한 미리보기
용도로만 남긴다.

### 라우팅을 어디서 하나

* **1차(지금 규모):** 백엔드(Spring)가 서브도메인 요청을 감지해 직접 프록시한다. 인증·소유권
  확인·프록시 로직이 이미 백엔드에 있으니 재사용이 쉽다.
* **확장 시:** 챌린지 트래픽이 백엔드로 다 몰리는 게 부담되면, 앞단에 전용 프록시(Traefik 등)를
  두고 Host→포트 라우팅을 넘긴다. 로드맵의 주소 지정 결정과 이어진다.

### 개발 환경

실제 와일드카드 DNS 없이도, `inst-<token>.127.0.0.1.nip.io` 처럼 IP로 해석되는 와일드카드
도메인을 쓰면 로컬에서 그대로 테스트할 수 있다.

## 3. Consequences (결과 및 영향)

### 🟢 장점

* **임의의 웹앱이 고침 없이 그대로 돈다.** 절대경로·JS·AJAX·쿠키 문제가 원천적으로 사라진다.
  CTF 웹 문제의 핵심 요구를 만족한다.
* 인스턴스마다 오리진(호스트)이 달라서 **쿠키·세션이 격리**된다. 문제 간, 그리고 백엔드와
  간섭이 없다.
* 포트를 **하나(80/443)만** 열어도 된다. 포트 풀처럼 여러 포트를 대외로 열지 않는다.
* 기존 프록시 전달 로직을 재사용한다. 바꾸는 건 "인스턴스를 경로가 아니라 Host에서 찾는다"뿐.

### 🔴 단점 / 개선안

* **와일드카드 DNS와 와일드카드 TLS 인증서가 필요하다**(운영). 개발은 nip.io류로 우회.
* 라우팅 계층이 **Host→포트 매핑을 실시간으로** 알아야 한다. 결과가 저장된 Redis나 에이전트의
  실시간 목록(List)에서 조회한다.
* **매 요청마다 소유권 검사**가 필요하다(세션 사용자 ↔ token 소유자). 빠뜨리면 남의 인스턴스가
  노출된다.
* **오픈 프록시/SSRF 주의.** token으로 매핑된 그 인스턴스의 loopback 포트 외에는 절대 프록시하지
  않도록, Host/token 화이트리스트로 대상 주소를 고정해야 한다.
* 백엔드가 라우팅까지 하면 챌린지 트래픽이 백엔드에 실린다. 지금 규모(수십 명)에선 괜찮지만,
  커지면 전용 프록시로 분리한다.

이 문서는 방향만 정한 기획이며, 실제 구현(서브도메인 매칭, token 발급·매핑, 소유권 검사,
DNS/TLS 설정)은 이번 범위가 아니다.
