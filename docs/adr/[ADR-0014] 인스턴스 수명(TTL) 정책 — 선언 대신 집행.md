* **날짜:** 2026-09-11
* **작성자:** 이도현
* **상태:** 제안됨 (기획, 아직 구현 안 함)

## 1. Context (배경)

지금 인스턴스에는 만료 시각이 붙어 나간다. 에이전트가 컨테이너를 띄우면서 계산한다
(`agent/internal/agentserver/handler.go`):

```go
// TODO TTL 설정 아직 안함
const perUserTTL = time.Hour
...
if req.IsolationType == "PER_USER" {
    res.ExpiresAt = time.Now().Add(perUserTTL).UTC().Format(time.RFC3339)
}
```

이 값은 조율자를 거쳐 웹까지 가고, 참가자에게 "이 인스턴스는 언제까지"로 보인다.

**그런데 그 시각이 되어도 아무 일도 일어나지 않는다.** 코드 전체에서 `ExpiresAt`을 쓰는 곳은
세 군데뿐이다 — 만드는 곳(에이전트), 옮겨 담는 곳(조율자), 스트림에 싣는 곳. **읽어서 지금
시각과 비교하는 코드가 없다.** 회수기(리퍼)가 없다.

즉 지금 만료 시각은 **지키지 않는 약속**이다. 참가자에게 한 시간이라고 말해놓고 컨테이너는
영원히 떠 있는다. 동아리 내부 수십 명 규모라 아직 티가 안 났을 뿐이고, 자원은 계속 샌다.

### 수명이 네 군데에 흩어져 있고 서로 모른다

| 무엇 | 어디 | 길이 |
| --- | --- | --- |
| 인스턴스 수명 | 에이전트 `perUserTTL` | 1시간 (하드코딩) |
| 결과 보관 | 웹 `CtfResultConsumer.RESULT_TTL` | 10분 |
| uuid → 소유자 매핑 | 조율자 `RedisCtfRequestProducer.OWNER_TTL` | 30분 |
| 문제 → uuid 매핑 | 웹 `InstanceProperties.mappingTtl` | 30분 |
| uuid → 컨테이너 기록 | 에이전트 `registry.Save` | **무기한** (`Set(..., 0)`) |

값들이 각자 정해졌고 관계가 문서에 없다. 그 결과 **인스턴스는 살아 있는데 쓸 수 없는 구간이
두 번** 생긴다.

* **10분 뒤** — 결과 보관이 끝난다. 웹이 `ctf:result:{uuid}`를 못 찾으니 참가자에게
  접속 주소를 다시 알려줄 수 없다. 컨테이너는 앞으로 50분 더 떠 있다.
* **30분 뒤** — 소유자 매핑이 끝난다. 서브도메인 프록시가 "이게 네 인스턴스가 맞나"를 확인할
  근거를 잃고 403을 돌려준다(ADR-0011의 소유권 검사). 컨테이너는 앞으로 30분 더 떠 있다.

참가자 눈에는 둘 다 "문제가 갑자기 안 열린다"로만 보인다.

### 그 외에 걸리는 것

* **1시간이 하드코딩이다.** 문제마다 필요한 시간이 다른데(간단한 SQLi vs 오래 걸리는 체인)
  코드를 고쳐야 바뀐다. `CreateInstance.md`에도 "나중에 웹이 보내는 요청 메시지에 TTL을
  추가한다"고 적어뒀지만 아직 아니다.
* **SHARED는 만료가 아예 없다.** `PER_USER`일 때만 `ExpiresAt`을 채운다. 의도된 것이긴 한데
  그 이유가 어디에도 적혀 있지 않아서, 다음 사람이 버그로 보고 고칠 수 있다.
* **registry 기록이 영원히 남는다.** `Set(ctx, key, id, 0)` — 만료가 없다. 컨테이너가 우리
  모르게 죽어도 `uuid:` 키는 남는다.
* **연장 수단이 없다.** 참가자가 한창 풀고 있는데 시간이 다 되면 그냥 끊긴다. 이게 가장 나쁜
  사용자 경험인데 지금은 만료 자체가 동작하지 않아 드러나지 않고 있다.

## 2. Decision (결정)

원칙 하나로 요약한다. **만료는 선언이 아니라 집행이다.** 시각을 계산해 보내는 것만으로는
아무것도 회수되지 않는다.

### TTL은 문제가 정하고, 웹이 실어 보낸다

에이전트의 `perUserTTL` 하드코딩을 없앤다. TTL은 문제 속성이므로 웹의 `Challenge`가 들고,
요청 메시지(`RequestMessage`)에 실어 보낸다.

* 웹이 안 보내면 **기본 1시간**을 쓴다. CTFd-Whale의 `docker_timeout` 기본값과 같다
  ([CTFd-Whale]) — 남들이 고른 값과 맞춰두면 나중에 근거를 다시 찾지 않아도 된다.
* 상한을 둔다. 문제마다 정하게 하되 관리자가 임의로 길게 잡아 호스트를 잠그지 못하게.

### 만료 시각은 에이전트가 한 번만 만든다

컨테이너를 띄운 직후 에이전트가 계산해서 **registry에 같이 기록**한다. 웹은 그 값을 받아
보여주기만 하고 다시 계산하지 않는다.

한 곳에서만 만드는 이유는 시계 때문이다. 계산하는 곳이 둘이면 두 시계가 어긋난 만큼 답이
달라지고, 그 차이는 "왜 1분 일찍 죽었나" 같은 모양으로 나타난다. 기준을 에이전트 시계
하나로 못박으면 어긋남이 생겨도 한 군데만 보면 된다.

### 회수는 주기적으로 훑어서 한다 — Redis 키 만료 이벤트를 쓰지 않는다

에이전트에 리퍼를 둔다. **30초마다** registry를 훑어 만료된 인스턴스를 내리고 기록을 지운다.

컨테이너를 만질 수 있는 유일한 조각이 에이전트라서다(ADR-0009). 조율자는 도커 소켓을 아예
안 본다(ADR-0012에서 compose의 마운트도 뺐다).

**registry 키에 TTL을 걸고 만료 이벤트를 구독하는 방식은 쓰지 않는다.** 간단해 보이지만
조용히 새는 실패를 만든다:

* Redis Pub/Sub은 fire-and-forget이다. 구독자가 잠깐 끊겼다 붙으면 그 사이 이벤트는 사라진다
  ([Redis keyspace notifications][redis-notif]). 에이전트를 재배포하는 몇 초 동안 만료된
  인스턴스는 **아무도 회수하지 않는다.**
* `expired` 이벤트는 **키에 접근할 때** 생성된다. TTL이 0이 되는 시점에 이벤트가 뜬다는 보장이
  없다 ([같은 문서][redis-notif]). 아무도 안 읽는 키는 한참 뒤에야 만료 이벤트가 난다.

놓친 이벤트 하나가 곧 영원히 떠 있는 컨테이너다. 주기적 조회는 놓쳐도 다음 주기에 다시 본다.

주기를 30초로 잡은 이유: CTFd-Whale은 10초마다 돈다. 우리는 동시 10~20개 규모라 그렇게
자주 볼 이유가 없고, 만료가 최대 30초 늦는 것은 참가자가 느끼지 못한다.

### 고아 회수는 라벨로 한다

registry 기록과 실제 컨테이너가 어긋나는 경우가 반드시 생긴다 — 기록을 쓰기 전에 죽거나,
기록을 지운 뒤 삭제에 실패하거나.

그래서 만료 시각을 **도커 라벨에도 박는다**(`nimda.ctf.expires`). 리퍼는 두 가지를 본다.

1. registry에 있는 것 중 만료된 것 → 내린다 (정상 경로)
2. `nimda.ctf` 라벨이 붙었는데 registry에 없는 컨테이너 → 고아다. 라벨의 만료 시각으로 판단해
   내린다

2번이 없으면 기록을 잃은 컨테이너는 영원히 남는다. 라벨은 ADR-0013에서 "사람이 골라볼
수단"으로 남겨둔 것인데, 여기서 회수의 2차 안전장치가 된다.

### SHARED는 만료하지 않는다 — 이유를 적어둔다

지금 동작 그대로 두되 근거를 남긴다. SHARED는 문제당 컨테이너 하나라 개수가 문제 수로
묶여 있고, 만료시키면 다음 참가자가 접속할 때마다 빌드를 기다린다.

대신 **놀고 있으면 내린다**(idle 회수)를 나중에 붙일 자리로 남긴다. 아무도 안 붙는 SHARED가
계속 떠 있는 것도 낭비이긴 하다.

### 보조 기록은 인스턴스보다 오래 살아야 한다

위의 "살아 있는데 못 쓰는 구간"을 막는 규칙이다.

```
결과 보관, 소유자 매핑, 문제→uuid 매핑  ≥  인스턴스 TTL + 여유(10분)
```

인스턴스를 가리키는 기록이 인스턴스보다 먼저 사라지면, 살아 있는 인스턴스를 못 찾거나
소유권을 확인 못 하게 된다. 지금은 이 순서가 거꾸로다.

TTL이 요청마다 달라지므로 이 값들도 고정 상수가 아니라 **인스턴스 TTL에서 유도**해야 한다.

### 연장(renew)은 자리만 잡아둔다

참가자가 풀고 있는데 끊기는 것을 막으려면 연장이 필요하다. CTFd-Whale도 연장을 제공하되
**횟수 상한**을 둔다([CTFd-Whale]) — 무제한이면 만료가 없는 것과 같아서다.

이번 범위에서는 만들지 않는다. 다만 만료 시각을 registry에 두기로 한 덕에, 연장은
"그 값을 미루고 라벨을 갱신하는 것"이 된다.

## 3. Consequences (결과 및 영향)

### 🟢 장점

* **약속을 지키게 된다.** 지금은 만료 시각을 말해놓고 아무것도 안 한다. 이 상태가 제일 나쁘다 —
  참가자는 끊길 걸 알고 대비하는데 실제로는 자원만 샌다.
* **"살아 있는데 못 쓰는 구간"이 사라진다.** 보조 기록 수명을 인스턴스에서 유도하므로
  10분·30분 절벽이 없어진다. 지금 있는 버그를 규칙으로 막는 것이다.
* **문제마다 시간을 다르게 줄 수 있다.** 코드를 안 고치고 문제 등록에서 정한다.
* **놓쳐도 다음 주기에 회수된다.** 이벤트 방식과 달리 실패가 누적되지 않는다.
* **기록을 잃어도 컨테이너는 회수된다.** 라벨이 2차 안전장치다.

### 🔴 단점 / 개선안

* **참가자가 예고 없이 끊긴다.** 만료가 실제로 동작하기 시작하면 지금 없던 불편이 생긴다.
  연장을 같이 만들지 않으면 "풀고 있었는데 날아갔다"가 나온다. 최소한 웹이 남은 시간을
  보여주고 끝나기 전에 알려줘야 한다.
* **최대 30초 늦게 회수된다.** 정확히 그 시각에 끊기지 않는다. 규모가 커지면 주기를 줄이거나,
  만료가 임박한 것만 따로 보는 식으로 바꿔야 한다.
* **리퍼가 삭제를 실패하면 조용하다.** 도커가 응답하지 않거나 컨테이너가 안 죽는 경우, 다음
  주기에 또 시도한다. 계속 실패하는 것을 알아챌 수단이 없으면 영원히 재시도만 한다 —
  연속 실패 횟수를 세서 알리는 정도는 필요하다.
* **시계에 의존한다.** 에이전트 시계가 크게 틀어지면 인스턴스가 일찍 죽거나 안 죽는다.
  단일 호스트라 지금은 위험이 작지만, 여러 대로 늘리면 시계 동기화가 전제가 된다.
* **registry를 매 주기 훑는다.** 지금 규모에서는 키 수십 개라 무시할 만하지만, 인스턴스가
  수백 개가 되면 `KEYS`/`SCAN` 비용이 생긴다. 만료 시각 기준 정렬 집합(sorted set)으로
  바꾸면 "지금 만료된 것만" 꺼낼 수 있다.
* **SHARED는 여전히 영원히 산다.** 이번 결정이 다루지 않는 부분이고, idle 회수를 붙이기
  전까지는 문제 수만큼 컨테이너가 계속 떠 있는다.
* **웹·조율자·에이전트를 같이 고쳐야 한다.** TTL이 요청 메시지에 추가되고 보조 기록 수명이
  유도값으로 바뀌므로, 세 조각이 한 번에 움직인다. ADR-0012의 메시지 계약도 같이 바뀐다.

### 코드

* `agent/internal/agentserver/handler.go` — `perUserTTL = time.Hour` 하드코딩과
  `// TODO TTL 설정 아직 안함`.
* `agent/internal/registry/registry.go` — `Set(ctx, key, id, 0)`, 만료 없는 기록.
* 웹 `CtfResultConsumer.RESULT_TTL` (10분), `InstanceProperties.mappingTtl` (30분),
  조율자 `RedisCtfRequestProducer.OWNER_TTL` (30분) — 서로 모르는 세 값.

### 외부 자료

* [Redis keyspace notifications][redis-notif] — Pub/Sub은 fire-and-forget이라 끊긴 동안의
  이벤트가 사라지고, `expired` 이벤트는 키에 접근할 때 생성되므로 TTL이 0이 되는 시점에
  뜬다는 보장이 없다. **키 만료 이벤트로 컨테이너를 회수하지 않기로 한 근거.**
* [CTFd-Whale][CTFd-Whale] — 같은 문제를 먼저 푼 선례. 컨테이너 수명 기본값
  `docker_timeout` 3600초, 횟수 상한이 있는 연장, 10초 주기 자동 정리. 기본 1시간과
  "연장은 상한과 함께"를 여기서 가져왔다.
