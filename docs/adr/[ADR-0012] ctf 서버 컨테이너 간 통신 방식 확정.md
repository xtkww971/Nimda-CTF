## 1. Context (배경)

기존 구조는 조율자(Provisioner)와 에이전트(Agent)가 **유닉스 소켓** 하나로 통신했다.
공유 볼륨(`ctf-run`)에 올라온 `/var/run/ctf/agent.sock` 파일을 에이전트가 리슨하고 조율자가
접속하는 식이다. 메시지는 길이 접두 JSON 프레임이고(`protocol/wire.go`), 요청 하나마다 연결을
열어 응답이 올 때까지 그 자리에서 기다리는 **동기 RPC**였다.

이 방식은 ADR-0009에서 두 조각을 한 호스트의 프로세스로 띄우기로 하면서 정해진 것이다.
소켓 파일의 소유자·권한으로 "누가 에이전트에 연결할 수 있는가"를 정할 수 있다는 게 근거였다.

돌려보니 다음이 걸렸다.

* **한 호스트를 벗어나지 못한다.** 유닉스 소켓은 같은 커널 안에서만 통한다. 지금은 단일 호스트가
  전제지만, 에이전트를 여러 대로 늘리는 순간 통신 방식부터 다시 짜야 한다.
* **TCP로 바꾸면 배선이 늘어난다.** 대안으로 TCP/IP를 검토했지만, 그러면 양쪽이 서로의 주소와
  포트를 알아야 한다. 조각이 늘어날 때마다 "누가 어디에 붙는지"를 정적으로 박아야 하고, 포트를
  미리 잡아두는 만큼 확장할 때 걸림돌이 된다.
* **오래 걸리는 일에 컨슈머 루프가 묶인다.** 이미지 빌드는 분 단위로 걸릴 수 있는데, 동기 RPC라
  그동안 조율자가 응답을 기다리며 서 있는다.
* **재시도 장치를 두 번 만들게 된다.** 웹 백엔드 ↔ 조율자는 이미 Redis Streams를 쓰고 있고,
  재시도·pending 회수·데드레터가 컨슈머 코드에 들어가 있다. 소켓 쪽은 연결 실패를 조율자가
  직접 재시도해야 해서, 같은 성격의 코드를 한 벌 더 갖게 된다.
* **어차피 공유 저장소가 필요해진다.** 조율자와 에이전트는 앞으로 인스턴스 현황(어느 유저의 어느
  문제가 어느 포트에 떠 있는지)을 같이 봐야 한다. ADR-0011의 서브도메인 프록시가 이 정보를
  요구한다. 소켓은 전달만 할 뿐 이걸 담아둘 곳이 없다.

## 2. Decision (결정)

조율자 ↔ 에이전트 통신을 **CTF 서버 전용 Redis(`ctf-redis`)의 Redis Streams**로 한다.

TCP로 직접 잇지 않고 Redis를 사이에 두는 이유는, 어차피 인스턴스 상태 동기화 때문에 공유
저장소가 필요하기 때문이다. 통을 하나 세우면 전달과 상태 공유를 같은 곳에서 해결할 수 있고,
양쪽은 서로의 주소가 아니라 **스트림 이름만** 알면 된다.

### 웹이 쓰는 Redis와 분리한다

`nimda-redis`(웹 백엔드와 공유)를 그대로 쓰지 않고 `ctf-redis`를 따로 띄운다.

* 저쪽은 웹 백엔드와 공유하는 데이터가 있고, 이쪽은 CTF 서버 내부 배선만 담는다.
  한 통에 섞으면 내부 스트림이 웹 쪽에서도 보인다.
* 메모리 상한을 따로 걸 수 없다. 내부 배선용 통이 웹 데이터와 같은 예산을 나눠 쓰게 된다.

조율자만 두 통을 다 본다. 웹 요청은 `nimda-redis`에서 받고, 에이전트에게 넘기는 일은
`ctf-redis`로 한다. 두 통을 잇는 것이 조율자의 역할이다.

### 스트림

| 스트림 | 방향 | 내용 |
| --- | --- | --- |
| `ctf:agent:ops` | 조율자 → 에이전트 | 인스턴스 생성/삭제 요청 |
| `ctf:agent:results` | 에이전트 → 조율자 | 생성/삭제 결과 |

컨슈머 그룹은 `ctf-agents`. 웹이 보는 스트림과 섞지 않는다 — 웹은 "인스턴스 하나 달라"까지만
알면 되고, 그걸 만드느라 오간 중간 메시지는 알 필요가 없다.

### 메모리 100MB

작은 통이다. 저장소가 아니라 전달 수단이고, 문제 인스턴스에 자원을 더 쓰자는 ADR-0009의
방향과도 맞는다. 세 값을 다르게 건다.

* `mem_limit: 100m` — 컨테이너 상한.
* `--maxmemory 80mb` — **일부러 낮게.** 컨테이너 한계까지 차오르면 redis가 판단할 틈도 없이
  커널이 죽인다. 20MB를 버퍼로 남겨 redis가 먼저 반응하게 한다.
* `--maxmemory-policy noeviction` — **큐라서 그렇다.** `allkeys-lru` 같은 걸 걸면 메모리가 찰 때
  redis가 조용히 스트림 엔트리를 지운다. 인스턴스 생성 요청이 소리 없이 사라진다는 뜻이다.
  차라리 쓰기를 실패시켜 조율자가 ACK하지 않고 재시도하게 두는 편이 낫다.

영속성(`save`, `appendonly`)은 끈다. RDB fork는 이 예산에서 부담이 크다.

Redis Stream은 ACK해도 엔트리가 지워지지 않으므로, 발행할 때 `MAXLEN ~ 10000`으로 근사
트리밍을 건다. 안 자르면 요청을 넣는 만큼 무한정 자라 예산을 채운다.

### 네트워크 분리

`ctf-internal` 망을 새로 판다.

* `ctf-redis` — `ctf-internal`만.
* `agent` — `ctf-internal`만. 웹 백엔드와도, 웹이 쓰는 redis와도 이야기할 일이 없다.
  필요한 건 `ctf-redis`와 호스트 도커 소켓뿐이다.
* `provisioner` — 두 망 모두. 웹의 redis를 보려면 `nimda-network`가, 에이전트와 이야기하려면
  `ctf-internal`이 필요하다.

호스트 포트는 열지 않는다. 정적 포트를 피하려는 것이 이 결정의 출발점이고, 컨테이너끼리는
서비스명 DNS로 붙으므로 잡아둘 이유가 없다.

### 권한 경계는 어디로 가나

ADR-0009에서 경계는 **소켓 파일의 소유자·권한**이었다. 소켓이 사라지면 그 근거도 사라진다.
대신 경계는 **망 소속**이 된다 — `ctf-internal`에 들어오지 못하면 에이전트에게 일을 시킬 수 없다.
"조율자는 컨테이너 런타임을 직접 만지지 않는다"는 실질적 방어선은 그대로 유지된다.

## 3. Consequences (결과 및 영향)

### 🟢 장점

* **정적 포트·주소 배선이 없다.** 양쪽이 아는 것은 스트림 이름뿐이다. 조각이 늘어나도
  "누가 어디에 붙는지"를 새로 박지 않는다.
* **재시도 장치를 한 벌만 갖는다.** pending 회수·데드레터·백오프가 이미 `queue.Consumer`에
  들어가 있고, 에이전트 통신도 그걸 그대로 쓴다.
* **에이전트가 죽어도 요청이 남는다.** 스트림에 그대로 있다가 살아나면 이어서 처리한다.
  소켓이었다면 연결 실패로 끝났다.
* **컨슈머 루프가 묶이지 않는다.** 조율자는 넘기고 바로 다음 요청을 본다. 빌드가 몇 분 걸려도
  상관없다.
* **인스턴스 상태 동기화의 자리가 생긴다.** ADR-0011의 프록시가 필요로 하는 현황을 같은 통에
  둘 수 있다.
* **에이전트를 웹 망에서 뺄 수 있다.** 통신이 `ctf-internal` 안에서 끝나므로 노출면이 줄어든다.

### 🔴 단점 / 개선안

동기 RPC를 비동기 메시지로 바꾸면서 치른 값이 대부분이다. 앞의 세 항목은 에이전트 쪽 컨슈머를
구현할 때 반드시 정해야 한다.

* **순서가 보장되지 않는다.** 컨슈머 그룹은 여러 컨슈머가 병렬로 꺼내가므로, 같은 인스턴스에
  대한 DESTROY가 CREATE를 앞지를 수 있다. 동기 RPC일 때는 요청 하나가 끝나야 다음이 갔으니
  순서가 저절로 지켜졌다. 에이전트를 여러 대로 늘리는 것이 이 결정의 명분 중 하나인데, 늘리는
  순간 이 문제가 실제로 터진다. 인스턴스 단위 잠금을 걸거나, 같은 키는 같은 컨슈머로 가도록
  나누는 방식이 필요하다.
* **같은 요청이 두 번 실행될 수 있다.** Redis Streams는 at-least-once다. 컨슈머가 처리 중에
  죽으면 pending 회수로 같은 메시지가 다시 배달된다. 그런데 `runtime.Run`은 같은 이름의
  컨테이너를 `docker rm -f`로 먼저 지우고 띄우므로, 참가자가 풀고 있던 인스턴스가 재배달 한
  번에 초기화된다. 이미 떠 있으면 그대로 두고 기존 host:port를 돌려주는 처리가 있어야 한다.
* **에이전트의 생사를 알 수 없다.** 소켓은 연결에 실패하면 즉시 "지금 에이전트가 없다"고
  알려줬다. 스트림 발행은 받는 쪽이 하나도 없어도 성공한다. 요청이 조용히 쌓이다 트리밍에
  잘려나갈 때까지 아무도 모른다. 컨슈머 lag이나 하트비트를 감시해야 이 침묵을 깰 수 있다.
* **재시작하면 처리 중이던 메시지가 사라진다.** 영속성을 껐기 때문이다. 게다가 조율자는
  에이전트에 넘긴 시점에 웹 메시지를 ACK하므로(`Consumer.process`는 결과가 없어도 ACK한다),
  그 요청은 어디에도 남지 않는다. 결과를 받은 뒤에 ACK하도록 바꾸거나, 이 통에 최소한의
  영속성을 켜는 선택지가 있다.
* **트리밍은 조용히 지운다.** `noeviction`으로 막으려던 바로 그 동작을 `MAXLEN`이 한다.
  다만 잘리는 지점이 만 건이라, 거기 닿았다는 것은 에이전트가 이미 멈춰 있다는 뜻이다.
  트리밍이 아니라 그쪽이 문제인 상황이므로 감수한다. 위의 lag 감시가 그전에 알려줘야 한다.
* **부품이 하나 늘었다.** 메모리 100MB에 더해, 죽으면 조율자와 에이전트가 서로를 잃는 단일
  장애점이 생겼다. 소켓일 때는 두 프로세스만 살아 있으면 됐다. 감시·재시작·업그레이드 대상이
  하나 늘어난다는 뜻이기도 하다. 불필요한 컨테이너를 만들지 않는다는 ADR-0009의 고려사항과
  상충한다.
* **스키마가 중복을 안고 간다.** 결과만 따로 오면 "어느 문제의 누구였는지"를 복원할 수 없어서,
  에이전트가 `challengeCode`/`userId`를 결과에 다시 실어 보낸다(`protocol.AgentResult`).
  양쪽이 같은 필드를 계속 맞춰야 하고, 한쪽만 바뀌면 결과를 웹으로 넘기지 못한다.
* **즉답 조회가 어색해진다.** `Status`/`List`처럼 물어보고 바로 답을 받아야 하는 것은 스트림에
  맞지 않는다. 조회용 엔드포인트를 에이전트로 옮기거나, 에이전트가 현황을 Redis 키에 써두고
  조율자가 읽는 방식으로 정해야 한다.
* **한 요청의 흐름이 두 스트림으로 쪼개진다.** 무엇이 왜 실패했는지 보려면 `ctf:agent:ops`와
  `ctf:agent:results`를 `requestId`로 이어 붙여야 한다. 소켓일 때는 한 함수 안에서 끝났다.
* **빌드 폴더를 누가 치울지 미정이다.** 소켓 시절엔 `Create`가 반환될 때 지웠지만, 이제 조율자는
  에이전트가 언제 빌드를 끝내는지 모른다. 에이전트가 빌드 후 지우거나 결과를 받은 뒤 조율자가
  지우거나 둘 중 하나로 정해야 한다. 안 정하면 `ctf-build` 볼륨이 계속 찬다.
* **망 소속이 곧 권한이다.** `ctf-internal`에 붙는 컨테이너는 무엇이든 에이전트에게 일을 시킬 수
  있다. 소켓 파일 권한처럼 세밀하지 않으므로, 이 망에 무엇을 넣는지 관리해야 한다. 더 조여야
  하면 Redis ACL로 스트림별 권한을 나누는 방법이 있다.

### 구현 현황

완료된 것:

* `protocol/stream.go` — 스트림 메시지 계약(생성/삭제 요청·결과, `AgentResult` 봉투)과 왕복 테스트.
* `provisioner/internal/agentclient/stream.go` — `Dispatcher` 인터페이스와 Redis Stream 구현.
* `provisioner/internal/queue/agent_result.go` — 결과 수신 컨슈머.
* `provisioner/internal/handler/router.go` — 문제 유형별 라우팅. 인스턴스가 필요한 유형(WEB)만
  에이전트로 보내고, 첨부파일만 있으면 되는 문제는 조율자가 presigned URL로 끝낸다.
* `provisioner/internal/handler/dispatch.go` — 에이전트로 넘기는 핸들러와 결과 변환.
* `provisioner/internal/config/config.go` — 스트림 키와 `CTF_AGENT_REDIS_ADDR`.
* `docker-compose.yml` — `ctf-redis`, `ctf-internal` 망, 메모리 상한.
* `provisioner/cmd/provisioner/main.go` 배선 — 두 통(nimda-redis / ctf-redis)을 각각 열고,
  생성 요청 컨슈머는 웹 통에서, 에이전트 결과 컨슈머는 CTF 통에서 돈다.

배선하면서 같이 정한 것:

* **`queue.Consumer`가 읽는 통과 쓰는 통을 나눈다.** 결과 컨슈머만 둘이 다르다 —
  `ctf-redis`의 `ctf:agent:results`를 읽어 `nimda-redis`의 결과 스트림에 발행한다.
  다른 컨슈머는 `pub`에 읽기 클라이언트를 그대로 넣는다. 데드레터는 항상 **읽은 통**에
  남긴다 — 못 처리한 메시지는 그 통의 문제지 웹에 보낼 결과가 아니다.
* **인스턴스가 필요 없는 유형이 인스턴스 스트림으로 오면 FAILED로 거절한다**
  (`handler/reject.go`). 첨부파일 문제는 `ctf:challenge:download:ops`로 와야 하고,
  `queue.Result`에는 `url` 필드가 없어 presigned URL을 대신 실어 줄 수도 없다.
  에러가 아니라 결과로 끝낸다 — 유형은 재시도해도 바뀌지 않는다.
* **`agentDeadLetterStreamKey` 기본값을 `ctf:agent:dead-letter`로 준다.** 비워 두면
  데드레터 `XADD`가 이름 없는 스트림으로 나간다.
* **`CTF_STATUS_ADDR`의 `GET /instances`를 뺐다.** 소켓 클라이언트의 `List`에 의존하던
  유일한 자리다. 아래 "즉답 조회가 어색해진다"를 정한 뒤에 다시 올린다.

남은 것:

* 에이전트 쪽 스트림 컨슈머(지금은 여전히 `net.Listen("unix", ...)`). 위의 🔴 중 순서
