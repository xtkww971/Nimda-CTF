## 1. Context (배경)

문제 인스턴스를 만들고 관리하는 일은 권한이 크기 때문에, 그 일을 두 조각으로 나눠 두었다
(ADR-0005, ADR-0007).

* **조율자(Provisioner):** Redis에서 요청을 받고, 판단하고, 결과를 돌려주는 일. 특별한 권한이 필요 없다.
* **에이전트(Agent):** 실제로 컨테이너를 만들고 띄우는 일. 컨테이너 런타임을 다룰 수 있는 유일한 조각.

처음에는 이 두 조각을 각각 별개의 도커 컨테이너로 띄우고, `/var/run` 아래 소켓 파일 하나로
서로 통신하게 하려고 했다.

하지만 조율자와 에이전트를 별개의 컨테이너로 나눠 관리하는 방식은 RAM 메모리를 많이 차지하고
권한의 경계가 조율자의 통신 방법을 생각했을 때 모호해진다는 점이 단점이다.

에이전트가 하는 일은 호스트의 컨테이너 런타임(도커)을 직접 부리는 것이다. 
하지만 에이전트를 컨테이너로 만들면, 컨테이너 안에서 다시 호스트의 도커를 제어해야 한다.
이를 구현하는 방법은 2가지이다.

* 호스트의 도커 소켓을 에이전트 컨테이너 안에 넣어준다 → 그 순간 그 컨테이너는 사실상
  호스트 전체를 만질 수 있게 된다. 이는 컨테이너 분리 이유 중 하나인 권한 분배의 원칙에 맞지 않는다.
* 컨테이너 안에 도커를 하나 더 띄운다 → 무겁고 오류 발생 가능성이 높다.

고려 사항:

* provisior와 agent의 권한을 확실하게 분리해야 한다.
* ctf 서버에서 문제를 제공하기 위해 컨테이너를 사용하는데 이때 최대한 많은 자원을 사용하기 위해 불필요한 컨테이너를 만들지 않는다.
* 소규모 ctf 서버이기에 단일 호스트로 서비스를 제공한다.

## 2. Decision (결정)

조율자와 에이전트를 각각 별개의 컨테이너로 띄우는 대신, **호스트에서 프로세스로 띄우고
OS가 관리(systemd 등)** 하도록 한다.

권한 분리는 컨테이너 경계 대신 OS 수준으로 지킨다.

* 두 프로세스를 서로 다른 OS 계정으로 실행한다.
* 에이전트는 컨테이너 런타임에 접근할 수 있는 계정으로, 조율자는 아무 권한 없는 계정으로 띄운다.
* 둘은 `/var/run` 아래 소켓 파일로만 통신하고, 그 소켓 파일의 소유자·권한으로 "누가 연결할 수
  있는가"를 정한다.

## 3. Consequences (결과 및 영향)

### 🟢 장점

* 컨테이너 안에서 다시 도커를 제어할 필요가 없어진다.
  컨테이너의 개수가 줄어들기 때문에 실제 문제 인스턴스에 자원을 더 쓸 수 있다.
  
* 권한 경계가 솔직해진다. 호스트 도커 소켓을 쥔 컨테이너는 격리된 것처럼 보이지만 사실상
  호스트 전체 권한이다. 그런 착시를 만들지 않고, "에이전트만 런타임을 만질 수 있고 조율자는
  못 만진다"를 OS 계정과 소켓 권한으로 분명히 드러낸다.

### 🔴 단점 / 개선안

* 컨테이너로 다 감싸는 방식보다 이식성이 떨어진다. 배포할 때 호스트 설정(서비스 등록, 계정,
  소켓 폴더)이 필요하다. 지금처럼 한 대에서 운영하면 괜찮지만, 나중에 여러 대로 늘리려면 다시
  생각해야 한다(단일 호스트 전제와는 맞는다).
* 조율자와 에이전트 사이의 격리가 별개 컨테이너보다 약하다. 다만 위에 적었듯 에이전트 쪽
  격리는 어차피 크게 의미가 없었고, 실제로 중요한 방어선(조율자는 런타임을 못 만진다)은 그대로
  유지된다.
* 소켓 파일 권한을 잘못 걸면 다른 계정이 에이전트에 연결할 수 있게 된다. 배포할 때 소켓
  소유자·권한 설정을 반드시 확인해야 한다.

위의 단점들은 배포 환경에서 문제가 된다.
하지만 CICD 스크립스를 사용하면 완화할 수 있고 나중에 문서로 다룰 예정
