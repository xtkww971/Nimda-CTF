## 1. Context (배경)

ADR-0015에서 게이트웨이를 두기로 하면서 이렇게 적었다.
-> 폭발 범위를 생각해서 웹사이트에서 프록시를 할 것임
> 로그인 세션의 사용자와 그 uuid의 소유자가 같은지 확인한다.

한 줄로 적었지만 **어떻게** 확인하는지는 안 적었다. 실제로 붙이려고 보니 그 한 줄이
"인증 코드를 어디에 두느냐"라는 큰 질문으로 이어졌다. 이 문서는 거기에 답한다.

### 판정에 필요한 재료가 전부 웹에 있다

"이 사람이 이 인스턴스에 들어가도 되나"를 판정하려면 두 가지가 필요하다.
지금 각각 어디 있는지 확인해봤다.

| 재료 | 무엇 | 지금 어디 있나 |
| --- | --- | --- |
| 신원 | 요청한 게 누구인가 | 웹 — JWT + user DB |
| 소유권 | 이 uuid가 누구 것인가 | 웹 — nimda-redis `ctf:request:owner:{uuid}` |

CTF 서버가 가진 건 ctf-redis의 `uuid → host:port` 하나뿐이다.
**판정할 재료가 아예 없다.**

그래서 실제 선택지는 "CTF가 인가를 하느냐 마느냐"가 아니라
**재료를 CTF로 옮길 것인가, 결정을 웹에서 받아올 것인가** 둘 중 하나다.

### 재료를 옮기는 건 비싸다 — 대칭키가 결정적이다

신원을 CTF가 판정하려면 토큰을 검증해야 하고, 그러려면 서명 키가 필요하다.
웹의 `JwtUtil`을 열어봤다.

```java
@Value("${jwt.secret}") private String secret;
this.key = Keys.hmacShaKeyFor(Decoders.BASE64.decode(secret));
...
.signWith(this.key, SignatureAlgorithm.HS256)
```

**HS256은 대칭키다. 검증 키와 발급 키가 같다.**

CTF에 "검증하라고" 이 키를 주면 **발급 권한을 같이 주는 것**이다. 임의의 userId로
토큰을 찍어낼 수 있다. 그리고 그 키를 받을 게이트웨이는 ADR-0015에서
**인터넷에 직접 노출되는 유일한 CTF 조각**이다. 가장 노출된 자리에 가장 민감한 비밀을
두는 셈이고, 뚫리면 인스턴스 하나가 아니라 플랫폼 계정 전체가 넘어간다.

RS256이었다면 얘기가 달랐다. 공개키만 주면 되니 검증은 되고 위조는 안 된다.
그게 표준 MSA 모양(OIDC + JWKS)이다. 지금은 아니다.

소유권 쪽도 마찬가지다. 소유권 매핑을 CTF가 가지려면 **CTF가 userId를 알아야 한다.**
그런데 그건 #148에서 일부러 뺀 것이다 — "CTF 서버는 요청한 사람이 누구인지 알 필요가
없다"가 이유였다. 인가 하나를 위해 그 결정을 되돌리는 셈이다.

### 게이트웨이는 권한을 쌓기에 가장 나쁜 자리다

게이트웨이가 놓이는 위치를 보면 두 가지가 겹친다.

* 인터넷에 직접 노출되는 유일한 CTF 조각이다 (ADR-0015).
* 참가자가 통제하는 코드 — 문제 컨테이너 — 바로 앞에 있다.

CTF 서버에서 가장 적대적인 자리다. 여기에 `jwt.secret`과 userId 매핑을 동시에 두면,
이 한 조각이 뚫렸을 때 나오는 것이 계정 전체 위조 + 누가 무슨 문제를 푸는지가 된다.

거꾸로 보면, **판정할 능력이 없는 상태로 두는 것 자체가 방어**다. 털려도 꺼낼 게 없다.

### 판정 로직이 이미 두 곳에 있다

같은 소유권 판정이 웹 안에 이미 둘이다.

* `ChallengeDownloadController.checkOwner` — 다운로드 링크
* `SubdomainInstanceProxyFilter` — 인스턴스 프록시

CTF로 옮기면 **세 곳**이 된다. 그것도 언어와 리포지토리가 다른 곳에. 규칙이 바뀔 때
세 군데를 같이 고쳐야 하고, 하나를 빠뜨리면 그게 구멍이 된다.

### 지금 구현은 배포 형태에서 동작하지 않는다

이 문서를 쓰면서 확인하다 발견한 것이라 같이 적어둔다.

```
인터넷 ──80/443──▶ nimda-nginx
                      │  server_name: api.nimda.kr *.nimda.kr  (이미 설정돼 있음)
                      ▼
                 backend-blue  (컨테이너, nimda-network, 127.0.0.1:8081:8080)
                      │
                      └─▶ http://127.0.0.1:32768   ← 이 컨테이너 안의 루프백

호스트 도커 데몬 ─────▶ 문제 컨테이너를 127.0.0.1:32768 에 publish
                                       ↑ 호스트의 루프백
```

`127.0.0.1`이 같은 곳을 가리키지 않는다. 에이전트는 `CTF_INSTANCE_HOST=127.0.0.1`을
결과에 실어 보내고, Spring은 그 값으로 `URI.create("http://" + host + ":" + port + ...)`을
만든다. Spring이 컨테이너 안에 있으므로 **자기 자신을 찌른다.**

IDE에서 직접 띄우면 우연히 동작하고, 컨테이너로 배포하면 막힌다.
게이트웨이가 에이전트와 같은 호스트에 놓이면 이 문제는 자동으로 사라진다.

## 2. Decision (결정)

**게이트웨이는 판정하지 않는다. 집행만 한다.**

### 인가를 두 단계로 나눈다

접근 제어에서 쓰는 표준 구분을 그대로 가져온다 ([NIST SP 800-207][nist-zta], [XACML][xacml]).

| | 하는 일 | 어디에 두나 |
| --- | --- | --- |
| **PDP** (판정) | "이 사람이 이 uuid의 주인인가" | **웹** — 재료가 여기 있다 |
| **PEP** (집행) | 판정에 따라 통과시키거나 막는다 | **게이트웨이** — 경로 위에 있다 |

"인가는 자원 소유자가 한다"는 원칙은 보통 판정과 집행이 같은 곳에 있는 경우를 전제한다.
여기는 어긋나 있다 — 자원은 CTF 것인데 판정 재료는 웹에 있다.
그 어긋남은 사고가 아니라 #148에서 이미 내린 결정의 결과다.

### CTF도 인가를 한다 — 자기가 아는 것만

판정을 전부 웹에 넘기는 게 아니다. 재료가 있는 쪽이 각자 판정한다.

| 판정 | 누가 | 근거가 어디 있나 |
| --- | --- | --- |
| 로그인했는가 | 웹 | JWT + user DB |
| 이 uuid의 주인인가 | 웹 | nimda-redis `ctf:request:owner:{uuid}` |
| 이 uuid가 존재하는가 | **CTF** | ctf-redis `uuid:` 레지스트리 |
| 아직 살아 있는가 (TTL) | **CTF** | ADR-0014 |
| 어디로 보낼 것인가 | **CTF** | `uuid → host:port` |

**사람에 대한 판정은 웹, 자원에 대한 판정은 CTF.**

이렇게 나누면 CTF 쪽이 오히려 강해진다. 웹이 "이 사람 통과시켜도 된다"고 해도
인스턴스가 이미 죽었으면 게이트웨이가 막는다. 웹은 그걸 알 수 없다.

### 어떻게 묻나 — 첫 진입만 물어보고 세션으로 굳힌다 
세션 생성 요청 UUID와 세션 요청 UUID가 같으면 인가
```
① 첫 진입
참가자 ──443──▶ 게이트웨이
                   │  (세션 쿠키 없음)
                   ├──▶ 웹 POST /internal/instance-access
                   │      Cookie: Authorization=<그대로 전달>
                   │      Body:   { "uuid": "..." }
                   │    ◀── 200 허용 / 401 미로그인 / 403 남의 것
                   │
                   ├──▶ ctf-redis: uuid 존재? TTL 남았나? 주소는?
                   │
                   └──▶ Set-Cookie: 이 서브도메인 한정 세션
                        그리고 컨테이너로 프록시

② 이후 요청
참가자 ──443──▶ 게이트웨이 ──▶ 컨테이너
                   └─ 세션 쿠키 + ctf-redis 조회만. 웹에 안 묻는다.
```

`/internal/instance-access`는 새로 만드는 게 아니라 **지금 있는 것을 떼어내는 것**에 가깝다.
`SubdomainInstanceProxyFilter`에서 프록시 부분을 버리고 소유권 검사 부분만 남기면 된다.
필터 순서 덕에 `SecurityContextHolder`에서 userId를 꺼내는 것도 그대로 쓴다.

### 왜 이 방식인가

**게이트웨이가 사용자를 식별할 수단을 하나도 갖지 않는다.** 키도, userId도,
토큰 포맷 지식도 없다. 쿠키를 그대로 웹에 넘기고 예/아니오만 받는다.
웹이 HS256을 RS256으로 바꾸든 세션 방식으로 갈아타든 CTF는 안 바뀐다.

이 한 줄을 결정으로 박아두는 것이 이 문서의 핵심이다. 나중에
"그냥 키 하나 공유하면 되잖아"로 새는 걸 막는다.

### 서명된 입장권 방식은 안 쓴다

웹이 접속 시점에 `HMAC(uuid, exp)` 티켓을 발급하고 게이트웨이가 서명만 검증하는 방식도
검토했다. 왕복이 아예 없고, 전용 키를 쓰면 털려도 위조되는 건 인스턴스 접근뿐이다.

접은 이유는 **공유할 비밀이 하나 생긴다**는 것이다. 로테이션과 배포 조율이 따라온다.
첫 진입만 묻는 방식이면 왕복 비용도 거의 같은데 비밀은 0개다. 지금 단계에서는
비밀을 안 만드는 쪽이 낫다.

나중에 웹이 RS256 + JWKS로 옮기면 그때 게이트웨이가 직접 검증하는 쪽으로 갈 수 있다.
forward auth로 시작해도 CTF 쪽 인터페이스는 그대로라 그때 바꿔도 된다.

### 세션 쿠키는 uuid에 묶고 서브도메인 밖으로 내보내지 않는다

게이트웨이가 심는 세션 쿠키는 **문제 컨테이너까지 전달된다.** 그 컨테이너는 참가자가
통제하는 코드가 도는 곳이다. 두 가지를 지킨다.

* **`Domain`을 부모 도메인으로 올리지 않는다.** 올리면 인스턴스 A가 인스턴스 B의
  입장권을 주워 쓴다.
* **쿠키 값을 uuid에 묶는다.** 다른 uuid로 재사용할 수 없어야 한다.
* 가능하면 **게이트웨이가 전달 전에 벗겨낸다.** 지금 `stripPlatformCookies`가 플랫폼
  쿠키에 하는 일과 같은 이유다.

### 수명은 ADR-0014의 규칙을 따른다

인가 근거에도 수명이 있다. 세션 쿠키 만료, nimda-redis의 `OWNER_TTL`,
ctf-redis 레지스트리 — 전부 ADR-0014가 정한 규칙을 받는다.

```
인가 근거 수명  ≥  인스턴스 TTL + 여유
```

지금 `OWNER_TTL`이 30분인데 인스턴스는 1시간을 산다. ADR-0014가 이미 적어둔
**"30분 뒤 본인이 403을 받는"** 절벽이 그대로다. 게이트웨이로 옮겨도 따라오므로 같이 고친다.

## 3. Consequences (결과 및 영향)

### 🟢 장점

* **게이트웨이가 뚫려도 나오는 게 없다.** 서명 키도 userId도 없다. 최악의 경우가
  "떠 있는 인스턴스에 무단 접근"에서 끝나고, 플랫폼 계정으로 번지지 않는다.
* **"CTF는 사용자를 모른다"가 끝까지 유지된다.** #148에서 메시지에서 userId를 뺀 결정이
  접근 제어까지 일관되게 이어진다. 원칙이 한 줄로 이어지면 나중에 판단이 쉬워진다.
* **판정 로직이 한 곳에 모인다.** 지금 웹 안에 둘로 갈라져 있는 소유권 검사를 엔드포인트
  하나로 합칠 수 있다. CTF로 옮겼다면 셋이 됐다.
* **웹이 인증 방식을 바꿔도 CTF는 안 바뀐다.** 토큰 포맷도 서명 알고리즘도 CTF 경계를
  넘지 않는다. RS256 전환이든 세션 전환이든 게이트웨이는 그대로다.
* **공유하는 비밀이 0개다.** 키 로테이션을 두 시스템이 같이 배포할 일이 없다.
* **왕복은 첫 진입 한 번뿐이다.** 이후 요청은 세션 쿠키와 ctf-redis 조회로 끝난다.

### 🔴 단점 / 개선안

* **웹이 인스턴스 접근의 런타임 의존이 된다.** 웹이 죽으면 새 인스턴스에 못 들어간다.
  이미 세션을 받은 쪽은 계속 쓸 수 있으니 전면 차단은 아니지만, 의존이 생기는 건 맞다.
  지금도 웹이 프록시하니 상황이 나빠지는 건 아니다.
* **게이트웨이가 상태를 갖게 된다.** 세션을 어딘가 저장해야 한다. ctf-redis에 넣으면
  되지만, "게이트웨이는 무상태"라고 말할 수 없게 된다.
* **세션 유효기간만큼 권한 회수가 늦다.** 판정 결과를 굳히는 대가다. 짧게 잡으면
  왕복이 늘고, 길게 잡으면 회수가 늦다. 어느 쪽이든 값을 치른다.
  다만 인스턴스가 죽는 경우는 공짜로 막힌다 — 게이트웨이가 어차피 ctf-redis에서
  주소를 찾아야 하므로, 기록이 없으면 세션이 살아 있어도 못 들어간다.
* **세션 쿠키가 문제 컨테이너에 노출된다.** 참가자 코드가 읽을 수 있다. uuid에 묶고
  전달 전에 벗겨내는 것으로 막지만, 빠뜨리면 조용히 구멍이 된다.
  `stripPlatformCookies`와 같은 종류의 "빠뜨리면 실패하는" 안전장치다.
* **웹에 내부 전용 엔드포인트가 생긴다.** `/internal/instance-access`가 외부에 노출되면
  안 된다. nginx에서 막든 네트워크로 가르든 장치가 필요하고, 이것도 빠뜨리면 구멍이다.
* **HS256 문제를 해결한 게 아니라 피한 것이다.** 웹의 대칭키 구조는 그대로 남는다.
  이 결정은 "CTF가 그 문제에 엮이지 않는다"까지만 한다. 웹 쪽 개선은 별도다.
  덧붙여 `JwtUtil`에는 필드 초기화가 `Decoders.BASE64.decode(secret)`인데
  `getSigningKey()`는 `secret.getBytes()`를 쓰는 불일치가 있다. 같이 볼 문제다.
* **인스턴스가 늘면 첫 진입 왕복이 몰린다.** 대회처럼 동시에 수백 명이 시작하는 상황에서
  웹에 순간 부하가 간다. 캐시나 배치를 고민해야 할 수 있다.

  매 요청 소유권 검사. 지금 `SubdomainInstanceProxyFilter`가 그 구현이고,
  이 문서에서 판정 부분만 남기고 집행을 게이트웨이로 넘긴다.
* 웹 리포 `Dosc/Issues/#148.md` — 메시지에서 userId를 뺀 결정.
  "CTF는 사용자를 모른다"의 출처이고, 이 문서가 그 원칙을 접근 제어까지 연장한다.

### 외부 자료

* [NIST SP 800-207 Zero Trust Architecture][nist-zta] — Policy Decision Point와
  Policy Enforcement Point를 나누는 모델. 집행 지점이 판정 권한을 갖지 않는다는 구성이
  이 문서의 뼈대다.
* [OASIS XACML 3.0][xacml] — PDP/PEP/PIP 용어의 출처. 판정과 집행을 분리하는 표준 어휘.
* [RFC 8725 — JWT Best Current Practices][rfc8725] — 대칭 서명은 키를 가진 모든 당사자가
  토큰을 발급할 수 있으므로 신뢰 경계를 넘어 공유하지 말라는 권고.
* [RFC 7517 — JSON Web Key (JWK)][rfc7517] — 비대칭 전환 시 공개키를 배포하는 표준 방식.
  나중에 RS256으로 갈 때의 목적지.
* [nginx `ngx_http_auth_request_module`][nginx-authreq] — 리버스 프록시가 외부에
  인가를 묻는 표준 패턴. 게이트웨이를 직접 만들지 않을 경우의 기성 수단.
* [Traefik ForwardAuth 미들웨어][traefik-fa] — 같은 패턴의 다른 구현.
  요청을 인증 서버로 보내고 2xx면 통과시키는 동작이 이 문서의 ①과 같다.
* [oauth2-proxy][oauth2-proxy] — 첫 진입에서 확인하고 자체 세션 쿠키로 굳히는 방식의
  실제 구현. ②로 넘어가는 구조의 선례.
* [OWASP Authorization Cheat Sheet][owasp-authz] — 인가 판정을 한 곳에 모으고
  집행 지점을 신뢰 경계 밖에 두지 말라는 권고.
