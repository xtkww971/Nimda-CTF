* **작성자:** 이도현
* **상태:** 제안됨 (기획, 아직 구현 안 함)

## 1. Context (배경)

지금 인스턴스 포트는 도커 데몬이 마음대로 고른다. 에이전트가 컨테이너를 띄울 때
호스트 포트를 비워서 넘기기 때문이다 (`agent/internal/runtime/docker.go`):

```go
PortBindings: nat.PortMap{
    containerPort: []nat.PortBinding{{HostIP: "127.0.0.1", HostPort: ""}},
},
```

`HostPort`가 빈 문자열이면 데몬이 비어 있는 포트를 하나 잡아준다. 에이전트는 컨테이너를
띄운 뒤 그 값을 되읽어 `host:port`로 조율자에게 돌려주고, 조율자가 웹으로 넘긴다.

여기까지는 굴러간다. 웹해킹 문제는 ADR-0011의 서브도메인 프록시가 앞에 서서 포트를
감춰주고, 규모도 동아리 내부 수십 명이라 부딪힌 적이 없다. 그래서 지금까지 미뤄왔다.

미뤄둔 채로 두면 걸리는 것들은 이렇다.

* **어느 포트가 나올지 우리가 말할 수 없다.** 이 호스트의 커널 설정은
  `net.ipv4.ip_local_port_range = 32768 60999`이고, 실제로 인스턴스가 받은 포트는
  32777·59588·59644였다. 전부 그 범위 안이다. 그런데 도커 버전에 따라 커널 설정을 무시하고
  49153~65535에서 고르기도 한다([moby#43054]). 즉 "인스턴스용 포트는 여기서 여기까지"라고
  적어둘 수가 없다. 방화벽 규칙도, 문제 설명서도 그 위에 못 쓴다.

* **나가는 연결과 같은 대역을 쓴다.** `ip_local_port_range`는 원래 *나가는* 연결이 출발
  포트를 고르는 범위다. 조율자가 S3에 붙고 redis에 붙을 때마다 그 대역에서 포트를 하나씩
  쓴다. 데몬이 인스턴스에 공개할 포트도 같은 대역에서 고르므로, 드물게 겹치면 컨테이너
  실행이 `bind: address already in use`로 실패한다. 산발적이고 재현이 안 되는 실패라
  제일 나쁜 종류다.

* **포트가 컨테이너 수명에만 묶여 있다.** 인스턴스를 다시 띄우면 포트가 바뀐다. 그런데 웹은
  결과를 `ctf:result:{uuid}`에 **10분 캐시**한다. 그 사이에 컨테이너가 재생성되면 웹은 이미
  죽은 포트를 참가자에게 안내한다. 참가자 눈에는 "문제가 안 열린다"로만 보인다.

* **pwn 문제를 담을 수 없다.** ADR-0011이 후속 과제로 남겨둔 부분이다. pwn은 참가자가
  `nc host port`로 직접 붙어야 하는데, 매번 달라지는 임의 포트는 대외로 열 수도 없고
  문제 설명에 적을 수도 없다.

* **인스턴스 수에 상한을 걸 수단이 없다.** 지금은 동시에 몇 개까지 뜰 수 있는지 아무도
  모른다. 포트가 곧 자원인데 그 자원을 세는 곳이 없다.

고려 사항:

* 규모는 동아리 내부 수십 명, 동시 인스턴스 10~20개다(ADR-0007). 크게 만들 이유가 없다.
* 단일 호스트가 전제다(ADR-0009).
* 웹 문제는 이미 서브도메인 프록시라는 답이 있다(ADR-0011). 포트를 참가자에게 보일 필요가
  아예 없다.
* "어느 요청이 어느 컨테이너인가"는 이미 공유 redis에 `uuid:` 접두사로 기록하고 있다
  (ADR-0012 이후). 포트를 같이 둘 자리가 이미 있다.

## 2. Decision (결정)

포트를 **하나의 문제로 다루지 않는다.** 용도가 둘이고 요구가 정반대라서다.

| | 웹(HTTP) 문제 | pwn(raw TCP) 문제 |
| --- | --- | --- |
| 참가자가 보는 것 | `inst-{uuid}.도메인` | `호스트 주소 + 포트` |
| 포트가 대외에 열리나 | 아니오 | 예 |
| 포트가 바뀌어도 되나 | 상관없다 | 안 된다 |

### 웹 문제 — 포트를 내부 구현으로 못박는다

지금 방식을 그대로 둔다. 데몬이 고르는 loopback 임의 포트다. 대신 **그 포트는 밖으로
나가지 않는다**는 것을 규칙으로 정한다.

* 참가자에게는 포트를 보여주지 않는다. 접속은 ADR-0011의 서브도메인으로만 한다.
* 웹 결과 메시지의 `host`/`port`는 **프록시가 쓰는 값**이지 사용자에게 보여줄 값이 아니다.
* 포트가 바뀌어도 문제가 없게, 프록시는 매 요청마다 `uuid`로 현재 포트를 조회한다.
  10분 캐시된 값을 그대로 쓰지 않는다.

바꿀 것이 거의 없다. 지금 하고 있는 일을 "이게 의도다"라고 적어두는 쪽에 가깝다.

### pwn 문제 — 명시적 포트 풀에서 할당한다

`30000–30199` 처럼 **우리가 정한 범위**를 미리 잡고 거기서만 나눠준다.

범위를 이렇게 고른 이유:

* `ip_local_port_range`(32768–60999) **밖**이다. 나가는 연결과 겹치지 않으니 위의 산발적
  `address already in use`가 구조적으로 사라진다.
* 200개면 동시 인스턴스 10~20개 규모에 넉넉하다. 넉넉하지 않게 잡는 편이 낫다 — 풀이
  바닥나는 것이 곧 "인스턴스가 너무 많다"는 신호이기 때문이다.
* 방화벽에 `30000-30199/tcp` 한 줄로 적을 수 있다.

### 풀은 에이전트가 관리하고, 상태는 공유 redis에 둔다

풀을 들 주체는 **에이전트**다. 컨테이너를 실제로 만드는 유일한 조각이고, 이미
`uuid → 컨테이너` 기록을 들고 있다(ADR-0012).

상태는 메모리가 아니라 **공유 redis**에 둔다. 메모리에 두면 에이전트가 재시작할 때 풀이
비어버리는데, 컨테이너는 그대로 떠 있어서 이미 쓰는 포트를 다시 나눠주게 된다.

```
ctf:ports:free          (Set)     아직 안 나간 포트들
ctf:ports:taken:{port}  (String)  이 포트를 쓰는 uuid
uuid:{uuid}             (Hash)    컨테이너 ID + 할당된 포트
```

* **할당:** `SPOP ctf:ports:free`. 하나를 원자적으로 꺼낸다. 비어 있으면 그 요청은
  `FAILED`로 돌려준다 — "지금은 자리가 없다"를 참가자에게 알리는 편이, 어딘가에서 조용히
  겹치는 것보다 낫다.
* **반납:** 컨테이너를 내릴 때(`DESTROY`) `SADD`로 되돌린다.
* **분실 회수:** 반납을 못 하고 죽는 경우가 반드시 생긴다. 주기적으로 `taken` 목록과 실제
  떠 있는 컨테이너를 대조해, 컨테이너가 없는 포트를 풀로 되돌린다. TTL 리퍼를 만들 때
  같이 붙인다.

`uuid:{uuid}`는 지금 컨테이너 ID만 담는 문자열인데, 포트를 같이 담으려면 해시로 바꾼다.

### 지금 하지 않는 것

* **포트 풀의 실제 구현.** pwn 문제를 실제로 붙일 때 한다. 이 문서는 그때 무엇을 할지를
  정해두는 것까지다.
* **FRP 같은 전용 리버스 프록시 도입.** CTFd-Whale이 쓰는 방식이다([CTFd-Whale]) — HTTP는
  도메인으로 라우팅하고 TCP는 정해둔 포트 대역(예: 10000–10100)을 프록시가 중계한다.
  구조는 우리가 가려는 방향과 같지만, 부품이 하나 더 늘고 Swarm을 전제한다. 단일 호스트
  수십 명 규모에서는 값이 비싸다. 여러 호스트로 늘릴 때 다시 본다.

## 3. Consequences (결과 및 영향)

### 🟢 장점

* **산발적 포트 충돌이 구조적으로 사라진다.** 풀을 `ip_local_port_range` 밖에 두는 것만으로
  나가는 연결과 부딪힐 일이 없어진다.
* **방화벽에 적을 수 있는 범위가 생긴다.** 지금은 "어디로 열릴지 모른다"라서 대외 노출을
  아예 못 하고 있다.
* **인스턴스 수 상한이 공짜로 생긴다.** 풀 크기가 곧 동시 인스턴스 상한이다. 따로 쿼터를
  만들지 않아도 되고, 바닥나는 순간이 곧 경고다.
* **웹 문제는 바꿀 것이 거의 없다.** 이미 하던 일에 규칙만 붙인다.
* **pwn을 붙일 때 설계를 다시 하지 않아도 된다.** ADR-0011이 남겨둔 숙제의 절반이 여기서
  메워진다.

### 🔴 단점 / 개선안

* **부품이 하나 늘어난다.** 지금은 데몬이 알아서 하던 일을 우리가 들게 된다. 할당·반납·회수
  세 군데가 다 틀릴 수 있는 자리다. 특히 **반납 누락**은 조용히 쌓이다 어느 날 풀이
  바닥나는 모양으로 터진다 — 회수 작업을 같이 만들지 않으면 안 된다.
* **풀 크기를 미리 정해야 한다.** 너무 작으면 멀쩡한 요청이 거절되고, 너무 크면 상한으로서
  의미가 없다. 200은 지금 규모를 보고 고른 값이라 근거가 약하다. 실제 사용량을 재고 나서
  조정해야 한다.
* **redis가 또 하나의 단일 장애점이 된다.** ADR-0012에서 이미 통신이 redis에 얹혔는데
  포트 할당까지 얹힌다. redis가 죽으면 인스턴스를 새로 못 띄운다. (이미 떠 있는 것은
  영향이 없다.)
* **웹 결과의 `host`/`port`가 "보여주면 안 되는 값"이 된다.** 지금 웹 API는 이 값을 그대로
  응답에 싣고 있다. 규칙만 정해두고 코드를 안 고치면, 언젠가 프론트엔드가 그 값을 화면에
  띄운다. ADR-0011의 소유권 검사를 우회하는 경로가 되므로 **응답에서 빼는 작업이 따로
  필요하다.**
* **풀 밖의 포트를 쓰는 문제가 오면 답이 없다.** 한 문제가 포트를 둘 이상 열어야 하는 경우
  (예: 웹 + 별도 TCP 서비스)를 지금 설계는 담지 못한다. 인스턴스당 포트 하나를 전제한다.
* **단일 호스트 전제가 더 굳는다.** 포트 풀은 한 호스트의 자원이다. 에이전트를 여러 대로
  늘리면 호스트마다 풀이 따로 있어야 하고, 그러면 "어느 호스트의 몇 번 포트"가 되어
  주소 지정이 다시 문제가 된다.
