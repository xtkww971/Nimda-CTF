## 1. Context (배경)
온라인 저지 시스템은 문제당 대용량의 테스트 케이스(Input/Output)를 다루어야 함. 이를 데이터베이스나 메시지 큐, 혹은 캐시(Redis)에 직접 저장할 경우 다음과 같은 문제가 발생함.
* **메모리 부족:** 테스트 케이스 파일이 커질 경우 Redis 메모리 점유율이 급격히 상승하여 시스템 안정성을 저해함.
* **성능 병목:** 메시지 큐에 대량의 데이터를 함께 실어 보낼 경우 전송 효율 저하 및 처리량 급감 현상 발생
* **불필요한 데이터 부하:** 채점 서버는 코드 실행과 결과 판정이 핵심인데, 부수적인 데이터 전송으로 인해 자원 효율성이 떨어짐.

## 2. Decision (결정)
테스트 케이스(Input/Output 파일) 저장을 위해 **AWS S3**를 도입함. 메시지 큐에는 실제 파일 데이터가 아닌 S3 객체 참조 주소(URL)만을 담아 채점 작업 요청을 전달함.

## 3. Consequences (결과 및 영향)

### 🟢 장점
* **메모리 효율성 극대화:** Redis와 메시지 큐는 시스템 메타데이터와 작업 상태 신호 처리에만 집중할 수 있어 OOM(Out of Memory) 위험이 사라짐.
* **데이터 분산 및 부하 경감:** API 서버는 최소한의 문제 정보(ID, 제목, 제한 시간 등)만 관리하고, 채점 서버는 S3로부터 직접 대용량 파일을 다운로드하여 각 서버의 부하를 최적화함.
* **성능 최적화:** 웹 서버와 채점 서버 사이의 불필요한 데이터 전송을 제거하여 채점 엔진의 처리 효율을 높임.
* **확장성:** 대용량 파일 저장을 S3로 외부화함으로써 인프라 확장이 유연해짐.

### 🔴 단점 / 개선안
* **네트워크 지연:** S3로부터 파일을 다운로드하는 과정에서 네트워크 지연이 발생할 수 있음.
* **개선안:** 채점 서버의 워커 노드에서 **RAM Disk(tmpfs)**를 활용한 로컬 캐싱을 구현하여, 최초 1회 다운로드 이후에는 메모리 속도로 테스트 케이스에 접근하도록 최적화함. 단, 서버 사양에 맞게 메모리 크기를 정해야 하고 최대한 많은 요청을 받을 수 있도록 캐시 메모리 사용을 극대화 해야함
