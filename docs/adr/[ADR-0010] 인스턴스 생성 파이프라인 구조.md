## 1. Context (배경)

사용자가 컨테이너가 필요한 웹해킹 문제에 접근하면, 문제 컨테이너를 하나 띄워서 접속
주소(host:port)를 돌려줘야 한다. 이 일은 여러 조각을 거친다 — 웹 백엔드, 큐, 조율자,
에이전트, 그리고 다시 돌아오는 결과. 지금까지 이 조각들을 하나씩 만들었고, 이 문서는
**완성된 전체 흐름과 각 조각의 역할**을 기록한다.

핵심 제약은 앞선 결정들에서 이미 정해져 있었다.

* 컨테이너 런타임을 다루는 일은 권한이 크므로, 그 일만 하는 조각(에이전트)을 따로 둔다
  (ADR-0007). 나머지(조율자)는 권한 없이 돈다.
* 조율자는 컨테이너로, 에이전트는 호스트 프로세스로 띄우고 소켓으로만 통신한다 (ADR-0009).
* 큐는 Redis Streams를 쓴다 (ADR-0004).

## 2. Decision (결정)

아래 흐름으로 인스턴스를 만든다.

```
[웹 백엔드(Spring)]                         [조율자(Go, 컨테이너)]            [에이전트(Go, 호스트 프로세스)]
  문제 접근                                       │                                    │
  ── 요청 발행 ──▶ Redis Stream ── 소비 ──▶  큐에서 요청 읽기                          │
     ctf:instance:ops                          S3에서 문제 zip 다운로드                │
                                               공유 폴더에 압축 해제 (한 번)           │
                                               ── 소켓(create, 폴더 경로) ──▶  그 폴더에서 Dockerfile 찾아 빌드
                                                                                컨테이너 실행, 포트 열기
                                               ◀── 결과(host:port) ──         결과 반환
  결과 저장 ◀── 소비 ──  Redis Stream ◀── 결과 발행 ──┘
  (requestId로 조회)      ctf:instance:results
```

조각별 역할:

* **웹 백엔드(Spring):** 사용자 요청을 받아 생성 요청을 `ctf:instance:ops` 스트림에 발행하고,
  돌아온 결과를 `ctf:instance:results` 스트림에서 소비해 `requestId` 키로 Redis에 잠깐
  저장한다. 사용자는 저장된 host:port로 (백엔드 리버스 프록시를 거쳐) 인스턴스 화면을 본다.
* **조율자(Provisioner):** 큐에서 요청을 꺼내 S3에서 문제 파일을 받고, **공유 폴더에 압축을
  한 번 푼 뒤 그 폴더 경로를 에이전트에게 넘긴다.** 에이전트가 돌려준 결과를 결과 스트림에
  발행한다. 권한이 필요 없고, 컨테이너 런타임은 전혀 만지지 않는다.
* **에이전트(Agent):** 넘겨받은 폴더에서 Dockerfile을 찾아 이미지를 빌드하고 컨테이너를 실행한
  뒤, 열린 포트를 조율자에게 돌려준다. 컨테이너 런타임을 다루는 유일한 조각.

두 방향 모두 별도의 Redis 스트림을 쓴다 — 요청은 `ctf:instance:ops`, 결과는
`ctf:instance:results`. 조율자와 에이전트 사이는 소켓 하나로만 통신하며, 메시지 형식은
양쪽이 공유하는 프로토콜 모듈 하나에 정의한다.

### 빌드 파일 전달: 소켓 스트리밍이 아니라 공유 폴더 경로

빌드 파일은 소켓으로 흘려보내지 않는다. 조율자가 S3에서 받아 **공유 폴더에 압축을 한 번 풀고,
그 폴더 경로만** 에이전트에게 넘긴다. 에이전트는 그 폴더에서 바로 빌드한다.
이렇게 하면 **압축을 한 번만** 푼다(예전엔 조율자가 tar로 묶고 에이전트가 다시 풀어 두 번 처리).
두 프로세스는 그 폴더를 공유 볼륨으로 같이 본다(ADR-0009의 배포 구조와 맞음).

### 지켜지는 보안 경계

조율자는 에이전트에게 **이미지 이름을 넘기지 않는다.** "어떤 문제(코드), 누가(유저), 그리고
빌드 폴더 경로" 만 보내고, 이미지 이름·마운트·네트워크·자원 제한은 에이전트가 스스로 정한다.
폴더 경로는 넘기지만, 에이전트가 **허용된 빌드 루트 아래인지 검사**해서 임의 호스트 경로(예: `/`)를
빌드 컨텍스트로 삼는 것을 막는다. 그래서 조율자가 뚫려도 임의 이미지·임의 경로로 컨테이너를
실행하게 만들 수 없다 (ADR-0007).

## 3. Consequences (결과 및 영향)

### 🟢 장점

* 각 조각의 책임이 분명하다. 조율자는 "무엇을·누구를"만 알고, 에이전트는 "어떻게 띄울지"만
  안다. 한쪽을 고쳐도 다른 쪽에 잘 번지지 않는다.
* 요청과 결과를 다른 스트림으로 나눠서 두 방향이 서로 간섭하지 않는다.
* **압축을 한 번만 푼다.** 조율자가 공유 폴더에 풀고 경로만 넘기므로, 소켓으로 큰 파일이
  오가지 않고 에이전트가 다시 풀 일도 없다.
* 실패해도 사용자에게 전달된다. 빌드나 실행이 실패하면 실패 결과를 그대로 결과 스트림에
  실어 보내므로, 사용자가 무한정 기다리지 않는다.

### 🔴 단점 / 개선안

* **조율자와 에이전트가 폴더를 공유해야 한다.** 경로로 넘기는 방식이라 두 프로세스가 같은
  파일시스템(공유 볼륨)을 봐야 한다. 배포 시 그 마운트를 맞춰야 하고, 에이전트의 빌드 루트
  검사를 반드시 켜야 한다(임의 경로 방지).
* **공유 인스턴스 재사용 미구현.** 지금은 요청마다 새로 만든다. 공유(SHARED) 문제는 이미
  떠 있는 컨테이너를 재사용해야 하는데, 그 로직은 후속 작업이다.
* **동적 플래그 주입 미구현.** 프로토콜에 플래그를 실을 자리는 있지만, 사용자별 플래그를
  계산해 넣는 부분은 플래그 설계(별도 ADR) 확정 후에 붙인다.
* **결과 소비는 auto-ack.** 결과 저장이 실패해도 메시지는 확인 처리된다. 저장이 멱등하고
  값싸서 지금은 괜찮지만, 더 엄격히 하려면 수동 ack로 바꾼다.
* **TTL 회수 미구현.** 결과에 만료 시각은 실어 보내지만, 실제로 만료된 컨테이너를 거둬가는
  리퍼는 아직 없다. 상시 운영에서 반드시 필요하므로 후속 작업.
