## 1. Context (배경)

ADR-0013에서 포트를 용도별로 나눴다. 웹은 loopback 임의 포트를 내부 구현으로 감추고,
pwn은 `30000-30199` 같은 명시적 풀에서 할당해 **방화벽에 범위 한 줄로 적는다**고 했다.

그 "방화벽에 한 줄"을 실제로 AWS에 올리려고 보니 걸리는 게 나왔다. 검토한 순서대로 적는다.

### 포트 범위를 지정하는 것 자체는 된다

도커는 컨테이너를 만들 때 포트 범위를 받는다.

```
docker run -p 8000-8010:80
```

Go SDK를 쓰는 지금 구조에서도 마찬가지로 옵션에 넣을 수 있다. 여기까지는 문제가 없다.

### 문제는 그 포트에 밖에서 닿으려면 방화벽에 적어야 한다는 것

AWS 인스턴스에서 포트에 접근하려면 보안 그룹에 그 포트가 명시돼 있어야 한다.
그러면 선택지가 둘이다.

* 범위를 통째로 열어둔다.
* 컨테이너가 뜨고 질 때마다 방화벽 규칙을 고친다.

### ipset을 먼저 생각했다가 접었다

리눅스 `ipset`으로 접근 권한을 테이블처럼 관리하는 방법을 먼저 봤다. 조회가 O(1)이고
포트 접근을 다루는 모듈을 따로 안 만들어도 된다는 게 장점이다.

접은 이유는 **끊는 쪽**이다. TTL이 지나 컨테이너를 내릴 때 ipset 항목도 지워야 하는데,
연결이 살아 있는 상태에서 규칙만 지우면 그 뒤 패킷은 **조용히 버려진다**. 클라이언트 OS는
그걸 거절이 아니라 유실로 보고 재전송을 반복한다. 참가자 화면에서는 즉시 끊기는 대신
한참 멈춰 있다가 타임아웃나는 모양이 된다.

찾아보니 AWS에서는 더 나빴다. 보안 그룹은 상태 저장(stateful)이라
**규칙을 바꿔도 이미 추적 중인 연결은 즉시 끊기지 않는다.** AWS 문서가 그렇게 적어뒀다
([보안 그룹 연결 추적][sg-tracking]):

> 보안 그룹 규칙을 변경해도 추적 중인 연결은 즉시 중단되지 않는다. 기존 연결이
> 타임아웃될 때까지 패킷을 계속 허용한다.

게다가 FIN이나 RST를 주고받지 않으면 그 연결은 **최대 5일까지** 유휴 상태로 남을 수 있다.
즉시 끊으려면 네트워크 ACL을 써야 하는데, 그건 서브넷 단위라 인스턴스 하나를 겨냥할 수 없다.

정리하면 **방화벽은 TTL을 집행하는 손잡이가 아니다.** ADR-0014에서 만료를 실제로 집행하기로
했는데, 방화벽 규칙을 고치는 것으로는 이미 붙어 있는 세션을 끊지 못한다.

### 권한은 어디서 확인하나

접근 URL을 한 번 내주고 나면, 그 뒤는 참가자 브라우저와 컨테이너 사이의 HTTP다.
에이전트는 그 사이에 낄 수 없다. 지금 파이프라인을 끝까지 적어보면 이렇다.

1. 유저가 컨테이너 생성을 요청한다.
2. nimda-redis에 요청이 저장된다.
3. 스트림에 저장된 데이터를 ctf-provisioner가 받는다.
4. 값을 꺼내 누락된 값이 없는지 확인한다.
5. Handler가 요청을 ctf-redis에 넣는다.
6. agent가 값을 꺼낸다.
7. agent_handler가 컨테이너를 생성한다.
8. 생성 완료 메시지를 ctf-redis에 넣는다.
9. ctf-provisioner가 생성 완료 메시지를 꺼낸다.
10. nimda-redis에 메시지를 전달한다.
11. 유저가 생성이 끝났음을 인지하고 연결을 시도한다 — 메시지에 접근 경로가 들어 있다.

**11번부터는 우리 코드가 관여하지 않는다.** 여기까지만 만들면 누가 누구의 인스턴스에 붙는지
구분할 수 없다.

nimda-redis에 `userId:UUID` / `UUID:url`을 두기로 했으니 그걸로 소유권을 볼 수는 있다.
다만 그러려면 **모든 요청이 우리를 거쳐야** 한다. 포트를 직접 노출하면 그 전제가 깨진다.

### 열어둔 포트에 아무나 노크하면

방화벽에 범위를 열어뒀는데 그 안의 포트에 컨테이너가 없는 경우를 생각해봤다.

요청이 오면 OS가 포트 상태를 보고 닫혀 있음을 확인한 뒤 클라이언트에 RST/ACK을 보낸다.
UDP면 ICMP Port Unreachable을 돌려준다. **결국 OS가 요청을 전부 처리한다.**
할당되지 않은 포트로 대량의 요청이 들어오면 그만큼 CPU를 쓴다.

그리고 컨테이너 상태 동기화가 어긋나면 유저가 요청하지 않은 컨테이너에 연결될 수 있다.
(이건 redis에 쌍으로 기록해두면 막을 수 있다.)

## 2. Decision (결정)

**인스턴스 포트를 대외로 열지 않는다. 80/443만 열고, 그 앞에 게이트웨이를 둔다.**

### 게이트웨이가 하는 일

```
참가자 ──443──▶ 게이트웨이 ──▶ 127.0.0.1:{인스턴스 포트}
                    │
                    └─ ctf-redis에서 uuid → 접근 정보 조회
                       nimda-redis에서 uuid → 소유자 확인
```

* 요청 헤더(Host)에서 `inst-{uuid}.{도메인}` 형태의 uuid를 꺼낸다.
* ctf-redis에 기록된 `uuid → 접근 정보`로 실제 컨테이너 주소를 찾는다.
* 로그인 세션의 사용자와 그 uuid의 소유자가 같은지 확인한다.
* 통과하면 패킷을 컨테이너로 넘기고, 웹 컨테이너가 처리한다.

인스턴스 포트는 loopback에만 열려 있으므로 게이트웨이를 거치지 않고는 닿을 수 없다.
방화벽에는 인스턴스 포트를 한 줄도 적지 않는다.

### 왜 이게 답인가

앞의 세 가지가 한 번에 풀린다.

* **방화벽을 건드릴 일이 없다.** 컨테이너가 뜨고 지는 것과 방화벽 규칙이 완전히 분리된다.
  ipset도, 동적 규칙 수정도 필요 없다.
* **TTL을 집행할 수 있다.** 만료된 인스턴스는 게이트웨이에서 막으면 그 즉시 막힌다.
  방화벽처럼 "기존 연결이 타임아웃될 때까지" 기다리지 않는다.
* **매 요청 소유권을 확인할 수 있다.** 모든 트래픽이 게이트웨이를 지나므로,
  URL이 새어나가도 남의 세션으로는 못 들어온다.

덤으로 닫힌 포트 노크 문제도 사라진다. 열려 있는 포트가 80/443뿐이라 OS가 응답해야 할
대상 자체가 없다.

### ADR-0011과의 관계 — 예고된 갈래로 가는 것

ADR-0011은 라우팅 위치를 이미 두 갈래로 적어뒀다.

* **1차(지금 규모):** 백엔드(Spring)가 서브도메인 요청을 감지해 직접 프록시한다.
* **확장 시:** 앞단에 전용 프록시를 두고 Host→포트 라우팅을 넘긴다.

지금 동작하는 건 1차다(`SubdomainInstanceProxyFilter`). 이 결정은 2차로 가는 것인데,
**가는 이유가 다르다.** ADR-0011은 "백엔드로 트래픽이 몰리는 부담"을 이유로 봤다.
여기서는 부담이 아니라 **포트를 열 수 없다는 제약**이 이유다. 규모와 무관하게 필요하다.

### 게이트웨이를 어디에 두나

CTF 서버 쪽에 모듈로 둔다. 인스턴스 주소를 아는 곳이 여기라서다 — `uuid → 컨테이너`
기록은 ctf-redis에 있고(ADR-0012), 포트를 정하는 것도 에이전트다(ADR-0013).

소유권 정보는 nimda-redis에 있으므로 게이트웨이는 두 통을 다 봐야 한다.
조율자가 이미 두 망에 걸쳐 있으니(ADR-0012의 `ctf-internal` + `nimda-network`) 같은 자리다.

### pwn은 이 결정으로 풀리지 않는다

게이트웨이는 HTTP를 본다. `nc host port`로 붙는 raw TCP는 Host 헤더가 없어서 담기지 않는다.
ADR-0013의 포트 풀은 **pwn에 한해서는 여전히 유효하다.**

다만 게이트웨이가 생기면 ADR-0011이 남겨둔 다른 갈래 — **웹 터미널**(xterm.js + WebSocket ↔
TCP 브리지) — 이 현실적인 선택지가 된다. 브라우저에서 WebSocket으로 게이트웨이에 붙고,
게이트웨이가 컨테이너의 TCP 소켓에 이어주는 방식이면 **pwn도 포트를 열지 않고 풀린다.**
그러면 대외 개방 포트는 끝까지 80/443뿐이다.

어느 쪽으로 갈지는 pwn을 실제로 붙일 때 정한다. 이 문서는 "게이트웨이가 있으면 그 선택지가
열린다"까지만 적어둔다.

## 3. Consequences (결과 및 영향)

### 🟢 장점

* **대외 개방 포트가 80/443뿐이다.** 공격 표면이 인스턴스 수와 무관해진다. 지금은 인스턴스가
  늘수록 열어야 할 포트도 는다.
* **방화벽과 컨테이너 수명이 분리된다.** 컨테이너가 뜨고 지는 일이 방화벽 규칙을 건드리지
  않는다. ipset이든 보안 그룹 API든, 동적으로 고치는 장치를 아예 안 만들어도 된다.
* **만료를 즉시 집행할 수 있다.** ADR-0014에서 정한 TTL 집행이 실제로 가능해진다.
  방화벽으로는 기존 세션을 못 끊는다.
* **모든 요청에서 소유권을 본다.** URL이 유출돼도 남의 세션으로는 못 들어온다.
* **포트가 바뀌어도 참가자에게 영향이 없다.** 게이트웨이가 매번 uuid로 현재 주소를 찾으므로,
  컨테이너를 다시 띄워 포트가 바뀌어도 접속 주소는 그대로다.

### 🔴 단점 / 개선안

* **모든 챌린지 트래픽이 한 점을 지난다.** 게이트웨이가 죽으면 떠 있는 인스턴스 전부에
  접근할 수 없다. 컨테이너는 멀쩡한데 아무도 못 붙는 상태가 된다 — 지금까지 만든 것 중
  가장 큰 단일 장애점이다.
* **부품이 또 하나 늘어난다.** ADR-0012에서 redis가 늘었고 여기서 게이트웨이가 는다.
  감시·재시작·배포 대상이 하나 더 생긴다. "불필요한 컨테이너를 만들지 않는다"는 ADR-0009의
  방향과 계속 멀어지고 있다.
* **매 요청마다 redis를 두 번 본다.** uuid → 주소, uuid → 소유자. 캐시하지 않으면 요청당
  왕복이 둘 붙는다. 캐시하면 만료·삭제가 늦게 반영되는 문제가 생긴다 — 어느 쪽이든 값을
  치른다.
* **게이트웨이가 두 망에 걸친다.** 소유권은 nimda-redis, 주소는 ctf-redis다. 두 통을 다
  보는 조각이 조율자에 이어 둘이 된다. 대신 웹이 소유권을 ctf-redis로 밀어넣는 방법도
  있는데, 그러면 웹 데이터가 내부 통에 섞인다(ADR-0012에서 통을 나눈 이유와 충돌).
* **와일드카드 DNS와 인증서가 전제가 된다.** `*.ctf도메인`에 대한 DNS와 TLS 인증서가 없으면
  서브도메인 방식 자체가 성립하지 않는다. 개발은 `nip.io`로 넘어가지만 운영은 아니다.
* **pwn은 여전히 미해결이다.** 이 결정은 HTTP만 덮는다. 포트 풀로 갈지 웹 터미널로 갈지
  정하지 않았고, 포트 풀로 가면 위의 "80/443만"이라는 장점이 깨진다.
* **Traefik 같은 기성품을 안 쓰기로 한 근거가 약하다.** Host 기반 라우팅은 이미 만들어진
  물건이 많다. 직접 만드는 이유는 소유권 검사를 붙여야 해서인데, 그건 인증 미들웨어로도
  된다. 만들기 전에 한 번 더 비교해봐야 한다.

  게이트웨이가 어디에 붙어야 하는지의 전제.
* [ADR-0009](<./[ADR-0009] 조율자·에이전트 배포 구조 — 컨테이너 분리 대신 프로세스 관리.md>) —
  부품을 늘리지 않으려던 방향. 이 결정이 그와 충돌하는 지점.

### 코드

* `agent/internal/runtime/docker.go` — `PortBindings`에서 `HostIP: "127.0.0.1"`로 묶는
  현재 구현. 인스턴스 포트가 이미 loopback에만 열려 있다는 근거.
* `agent/internal/registry/registry.go` — ctf-redis의 `uuid:` 기록. 게이트웨이가 주소를
  찾을 자리.
* 웹 백엔드 `SubdomainInstanceProxyFilter` — 지금 동작 중인 1차 라우팅. 게이트웨이가 이
  역할을 가져간다.

### 외부 자료

* [Amazon EC2 보안 그룹 연결 추적][sg-tracking] — 보안 그룹은 상태 저장이라 규칙을 바꿔도
  추적 중인 연결이 즉시 끊기지 않고, FIN/RST가 없으면 최대 5일까지 유휴로 남는다.
  즉시 끊으려면 서브넷 단위인 네트워크 ACL을 써야 한다.
  **"방화벽은 TTL 집행 수단이 아니다"의 근거.**
* [보안 그룹 규칙 — Amazon VPC](https://docs.aws.amazon.com/vpc/latest/userguide/security-group-rules.html) —
  인바운드 규칙에 포트를 명시해야 한다는 기본 동작.
* [CTFd-Whale][CTFd-Whale] — 같은 문제를 FRP로 푼 선례. HTTP는 도메인으로 라우팅하고
  raw TCP만 정해둔 포트 대역을 중계한다. 웹은 게이트웨이, pwn은 포트라는 이 문서의
  결론과 같은 모양이다.
