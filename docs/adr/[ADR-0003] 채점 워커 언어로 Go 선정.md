## 1. Context (배경)
채점 서버(Judge Worker)는 큐에서 제출물을 꺼내 컴파일/샌드박스 실행/결과 판정을 반복하는
워커 프로세스로, ADR-0001에서 이미 "채점 서버(Go Worker)"로 API 레이어(Spring Boot)와
역할을 분리하기로 전제하고 있었으나, Go를 채점 워커 언어로 선정한 근거 자체는 별도
ADR로 기록된 적이 없었음(#2 체크리스트의 미완료 항목).

고려 사항:
* 다수의 채점 요청을 동시에 처리해야 하며, 요청마다 컴파일러/샌드박스 프로세스를 기동하는
  I/O 및 프로세스 관리 위주 워크로드.
* 컨테이너 단위로 워커를 수평 확장(같은 Redis Consumer Group에 컨슈머 추가)하는 구조이므로,
  워커 하나의 런타임 오버헤드가 인스턴스 수만큼 곱해짐.
* API 레이어(Spring Boot, ADR-0001)와 달리 이 프로세스는 대외 HTTP API를 갖지 않고
  큐 소비 + OS 프로세스 제어가 핵심.

## 2. Decision (결정)
채점 워커(consumer) 구현 언어로 **Go**를 선정함. API/비즈니스 로직 레이어는 계속 Spring Boot를
사용하되(ADR-0001), 실제 코드 실행을 담당하는 워커는 Go로 분리한다.

## 3. Consequences (결과 및 영향)

### 🟢 장점
* **경량 동시성:** goroutine 기반 동시성 모델이 "요청마다 프로세스/스레드를 띄우고 기다리는"
  워커의 워크로드에 잘 맞고, JVM 스레드에 비해 컨텍스트당 자원 소모가 작음.
* **낮은 런타임 오버헤드:** ADR-0001에서 지적된 JVM의 리소스 오버헤드 문제를 워커 쪽에서는
  피할 수 있음. 워커를 여러 대로 수평 확장할 때 인스턴스당 메모리 비용이 작아 유리함.
* **단일 정적 바이너리:** 별도 런타임 설치 없이 배포/컨테이너 이미지가 가벼워짐 (콜드 스타트,
  스케일 아웃에 유리).
* **표준 라이브러리의 OS/프로세스 제어:** `os/exec`, syscall 등으로 컴파일러 실행, 리소스 제한
  적용(향후 샌드박스 구현) 같은 저수준 제어가 자연스러움.
* **성숙한 Redis 클라이언트:** 공식 권장 클라이언트인 `github.com/redis/go-redis`가 Streams
  Consumer Group(`XREADGROUP`/`XCLAIM`/`XAUTOCLAIM` 등)을 온전히 지원함 — 실제로 이번
  작업(`worker/`)에서 이 클라이언트로 큐 컨슈머를 구현해 검증함.

### 🔴 단점 / 개선안
* **Java 생태계 대비 라이브러리 부족:** Spring Boot 쪽처럼 방대한 프레임워크 지원은 없음.
  다만 워커의 책임 범위(큐 소비, 프로세스 실행, 결과 콜백)가 크지 않아 표준 라이브러리 +
  최소 의존성(현재는 go-redis 하나)으로 충분.
* **팀의 Go 숙련도:** 기존 웹 서비스가 Spring 기반이라 Go 러닝커브가 있을 수 있음. 워커의
  책임을 좁게 유지(큐 소비 + 채점 로직)해 학습 범위를 제한함.
