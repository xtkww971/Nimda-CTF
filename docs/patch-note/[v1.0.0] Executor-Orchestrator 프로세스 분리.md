# 🚀 Update v1.0.0 : Executor / Orchestrator 프로세스 분리 (ADR-0005 구현)

**배포일자:** 2026-08-03

> [ADR-0005](../adr/%5BADR-0005%5D%20Isolate%20%EA%B8%B0%EB%B0%98%20%ED%94%84%EB%A1%9C%EC%84%B8%EC%8A%A4%20%EC%83%9D%EC%84%B1.md)에서 정한 "isolate 호출 전담 프로세스(Executor)와 비즈니스 로직 프로세스
> (Orchestrator)를 나눈다"는 결정을 실제로 구현했다. 지금까지는 `worker` 모듈 하나가
> Redis 컨슈머부터 isolate `exec.Command` 실행까지 전부 담당했는데, 이번 패치로
> **완전히 별개의 Go 모듈(= 별개의 배포 프로세스)** 두 개로 쪼개고 그 사이를 로컬
> 유닉스 도메인 소켓 하나로 연결했다.

## 🏗️ 구조 개편 (Architecture)

### 전체 그림

```
┌───────────────────────────── 워커 컨테이너(호스트) ─────────────────────────────┐
│                                                                                 │
│   Redis Streams            ┌──────────────┐   유닉스 도메인 소켓   ┌───────────┐ │
│   (judge:submissions) ───▶ │ Orchestrator │ ─────────────────────▶ │ Executor  │ │
│   backend-spring 발행       │  (worker/)   │   /var/run/judge/     │(executor/)│ │
│                             │              │   executor.sock       │           │ │
│   S3 (테스트케이스 등) ◀──▶ │              │ ◀───────────────────── │           │ │
│                             └──────────────┘                        └─────┬─────┘ │
│                                                                            │       │
│                                                                            ▼       │
│                                                                    isolate(1) CLI   │
│                                                                    (setuid root)    │
│                                                                            │       │
│                                                                            ▼       │
│                                                                    격리된 box 안    │
│                                                                    (제출 코드 실행)  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 왜 두 모듈로 쪼갰나

기존에는 `worker`가 Redis도 읽고, S3도 읽고, **isolate도 직접 실행**했다. 이 구조의
문제는 ADR-0005가 지적한 그대로다 — 오케스트레이션 코드(메시지 파싱, S3 연동, 큐
재시도 로직 등)에 버그나 인젝션 취약점이 있으면, 그 프로세스가 곧 "제출 코드를
샌드박스에서 실행할 권한"을 가진 프로세스이기도 하므로 파급 범위가 곧바로
샌드박스 탈출로 이어질 수 있다. 2024년 Judge0 CVE들이 정확히 이 패턴(오케스트레이션
코드의 버그 → 특권 프로세스 전체 장악)이었다.

그래서 **"isolate를 실행할 수 있는 프로세스"와 "Redis/S3/판정 로직을 다루는
프로세스"를 물리적으로 다른 프로세스(다른 Go 바이너리, 다른 권한)로 쪼갰다.** 둘
사이의 유일한 접점은 로컬 유닉스 소켓 하나뿐이고, 그 소켓을 통해 오가는 정보는
"컴파일해줘 / 이 입력으로 실행해줘 / 결과 돌려줘" 뿐이다. Orchestrator는 isolate
명령어나 box 경로를 전혀 모르고, Executor는 기대 출력(expected output)이나 채점
판정 로직을 전혀 모른다.

### 모듈별 역할

| | **Executor** (`executor/`) | **Orchestrator** (`worker/`) |
|---|---|---|
| Go 모듈명 | `nimda-judge-executor` | `nimda-judge-worker` |
| 아는 것 | isolate CLI, box pool, 언어별 컴파일/실행 커맨드(`internal/language`) | Redis Streams, S3, 채점 판정 규칙(AC/WA/TLE/...) |
| 모르는 것 | 기대 출력, 채점 규칙, Redis/S3 자체 | isolate 실행 방법, box 파일 경로, 컴파일러 플래그 |
| 권한 | isolate 실행에 필요한 최소 권한만 (setuid isolate 바이너리 호출) | 비특권 — Redis/S3 자격증명만 가짐 |
| 진입점 | `cmd/executor/main.go` | `cmd/worker/main.go` |
| 핵심 패키지 | `internal/isolate`(CLI 래퍼), `internal/language`(언어 정의), `internal/execserver`(소켓 서버) | `internal/queue`(Redis), `internal/judge`(판정), `internal/executorclient`(소켓 클라이언트) |

이번 패치에서 **`Judge.Handler`를 실제 로직에 연결하는 배선(현재 `StubHandler`가
큐에 붙어있는 상태)은 범위에서 제외**했다 — 이미 스텁이고 별도 후속 작업이다.

## 🔌 통신 원리: 왜 TCP 포트가 아니라 유닉스 도메인 소켓인가

"포트 설정"을 물어봤다면 먼저 짚어야 할 게 있다 — **이 연결에는 포트가 없다.**
Executor와 Orchestrator는 `net.Listen("tcp", ":8080")` 같은 TCP 소켓이 아니라
`net.Listen("unix", "/var/run/judge/executor.sock")`, 즉 **유닉스 도메인 소켓
(Unix Domain Socket, UDS)** 으로 통신한다.

**TCP 소켓과의 차이:**
- TCP는 `IP:포트`로 주소를 잡고, 커널 네트워크 스택(패킷화, 체크섬, 라우팅 테이블 조회
  등)을 반드시 거친다 — 같은 머신 안에서 통신하더라도 루프백 인터페이스를 통과한다.
- 유닉스 소켓은 주소가 **파일시스템 경로**(`/var/run/judge/executor.sock`)다. 커널이
  이 경로를 두 프로세스 사이의 공유 메모리 파이프로 취급해서, 네트워크 스택을 아예
  거치지 않고 커널 버퍼로 데이터를 바로 복사한다. 그만큼 빠르고, 애초에 네트워크
  인터페이스에 열리는 포트가 없으니 **컨테이너 바깥이나 다른 호스트에서는 물리적으로
  접근할 방법이 없다.** 같은 마운트 네임스페이스(=같은 컨테이너, ADR-0005가 말하는
  "워커 컨테이너 안") 안에 있는 프로세스만 이 경로를 열 수 있다.
- 소켓 파일 자체에 유닉스 파일 권한(owner/group/mode)을 걸 수 있어서, 원한다면
  "Orchestrator를 실행하는 유저만 이 소켓에 연결 가능"하도록 추가로 제한할 수도 있다
  (현재는 별도 권한 제한 없이 기본 권한으로 생성됨 — 필요하면 후속 작업).

즉 "포트 설정"에 대응하는 것은 **소켓 파일 경로 설정**이고, 아래 환경변수로 조정한다.

### 설정값 (포트 대신 경로/환경변수)

| 환경변수 | 어느 쪽 | 기본값 | 의미 |
|---|---|---|---|
| `EXECUTOR_SOCKET_PATH` | Executor (`cmd/executor/main.go`) | `/var/run/judge/executor.sock` | 이 경로에 `net.Listen("unix", ...)`으로 바인딩 |
| `EXECUTOR_SOCKET_PATH` | Orchestrator (`worker/internal/config/config.go`) | `/var/run/judge/executor.sock` | Orchestrator가 `net.Dial("unix", ...)`할 대상 |
| `EXECUTOR_BOX_POOL_SIZE` | Executor | `4` | 동시에 열어둘 수 있는 isolate box 개수 (`isolate.NewBoxPool(n)`) |
| `EXECUTOR_META_DIR` | Executor | `/tmp/judge-meta` | isolate가 실행 결과 meta 파일을 쓰는 box 바깥 임시 디렉토리 |
| `EXECUTOR_ISOLATE_BIN` | Executor | `isolate` (PATH에서 탐색) | isolate 바이너리 절대경로를 고정하고 싶을 때 |

두 값(`EXECUTOR_SOCKET_PATH`)은 **같은 경로를 가리켜야 한다** — 둘 다 같은 컨테이너의
같은 파일시스템 경로를 보고 있어야 연결된다. `executor/cmd/executor/main.go`는 기동 시
이 경로에 이미 파일이 남아있으면(비정상 종료로 인한 잔여 소켓) 먼저 지우고 새로
`Listen`한다.

## 📡 프로토콜: 세션 기반 JSON 스트리밍

### 왜 "세션"인가

한 제출을 채점할 때 실제로 필요한 순서는 **"컴파일 1번 + 테스트케이스 N번을 같은
box 안에서"** 다. 매 테스트케이스마다 새 연결/새 box를 만들면 컴파일을 N번 반복하는
꼴이라 비효율적이고, 반대로 아예 통짜로 "테스트케이스 전부 실행해서 한번에 결과
줘"로 만들면 **첫 테스트케이스에서 실패했을 때 나머지를 생략하는 최적화
(`StopOnFirstFail`)를 할 수 없다** (Executor가 이미 다 실행해버린 뒤에 결과를 받으므로).

그래서 **연결 하나 = 세션 하나**로 설계했다. 소켓 연결을 맺으면 그 연결 위에서
`Start` → `Run`(테스트케이스 수만큼 반복) → `End` 순서로 여러 번 주고받고, 마지막에
연결을 닫는다. Orchestrator는 `Run` 응답을 보고 그 자리에서 바로 실패로 판정하면
**다음 `Run`을 아예 보내지 않고 곧장 `End`를 보낼 수 있다** — 지금 코드와 똑같이
실제 실행 자체를 생략한다.

### 왜 길이 프리픽스가 없나

일반적으로 소켓으로 메시지를 여러 개 주고받으려면 "이번 메시지는 몇 바이트인지"를
앞에 붙이는 길이 프리픽스 프레이밍이 필요하다(TCP는 스트림이라 메시지 경계가 없으므로).
여기서는 그 대신 Go 표준 라이브러리 `encoding/json`의 `Decoder.Decode()` 특성을
그대로 이용한다 — `Decoder`는 스트림에서 유효한 JSON 값 하나를 파싱하고 나면 정확히
그 값의 끝에서 멈추고, 다음 `Decode()` 호출은 이어서 그 다음 JSON 값부터 다시 읽는다.
즉 `{...}{...}{...}`처럼 JSON 객체를 이어붙여 보내기만 해도 양쪽이 정확히 하나씩
읽어낼 수 있다. 별도 프레이밍 계층 없이 표준 라이브러리만으로 세션 프로토콜을
구현할 수 있는 이유다.

### 메시지 봉투 (Frame)

모든 메시지는 `type` 필드로 무엇을 실어 나르는지 구분되는 봉투에 담긴다.

```go
// executor/internal/execserver/protocol.go (Executor 쪽 정의)
type RequestFrame struct {
    Type  FrameType     `json:"type"`            // "start" | "run" | "end"
    Start *StartRequest `json:"start,omitempty"`
    Run   *RunRequest   `json:"run,omitempty"`
}

type ResponseFrame struct {
    Type  FrameType      `json:"type"`
    Start *StartResponse `json:"start,omitempty"`
    Run   *RunResponse   `json:"run,omitempty"`
    Error string         `json:"error,omitempty"` // 채워지면 요청 실패 (Orchestrator는 IE로 처리)
}
```

`worker/internal/executorclient/protocol.go`에 **같은 JSON 모양을 손으로 미러링**한
버전이 하나 더 있다. 두 모듈이 서로를 `import`하지 않게 하기 위한 의도적인 중복이다
(모듈 간 Go 의존성이 생기면 "완전히 분리된 프로세스"라는 설계 의도가 약해진다). 대신
두 파일 상단 주석에 "반대편 파일과 동기화 유지"를 명시해뒀다 — 필드를 바꿀 땐 두
파일 다 고쳐야 한다.

### 시퀀스

```mermaid
sequenceDiagram
    participant O as Orchestrator (judge.go)
    participant E as Executor (execserver)
    participant I as isolate CLI

    O->>E: connect (unix socket)
    O->>E: StartRequest{language, sourceCode}
    E->>E: box 획득 (BoxPool.Acquire)
    E->>E: 소스 기록 (box.WriteFile)
    E->>I: isolate --run (컴파일 커맨드)
    I-->>E: exit code / stderr
    E-->>O: StartResponse{compileOk, compileMessage}
    alt 컴파일 실패
        O->>E: EndRequest (box 정리하고 종료)
        O->>O: JudgeResult{Verdict: CE}
    else 컴파일 성공
        loop 테스트케이스마다
            O->>E: RunRequest{stdin, timeLimitSec, memoryLimitKb}
            E->>I: isolate --run (실행 커맨드, 같은 box)
            I-->>E: meta 파일(exit code/시간/메모리) + stdout
            E-->>O: RunResponse{status, timeSec, maxRssKb, stdout, ...}
            O->>O: classify() -> AC/WA/TLE/MLE/RE/OLE 판정
            opt 실패 &amp; StopOnFirstFail
                Note over O: 이후 RunRequest를 보내지 않고 루프 탈출
            end
        end
        O->>E: EndRequest
        E->>E: box 정리 (BoxPool.Release)
    end
    E-->>O: EndResponse
    O->>O: connection close
```

### 메시지별 필드

**StartRequest** — box를 열고 소스를 기록 + (필요하면) 컴파일한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `language` | string | `"c11"`/`"cpp17"`/`"python3"`/`"java17"` 등, Executor의 `language.Languages` 맵 키 |
| `sourceCode` | []byte | 제출된 소스코드 원문 |
| `useCgroups` | bool | isolate에 `--cg`를 쓸지 여부 (cgroup 기반 메모리 측정) |

**StartResponse**

| 필드 | 설명 |
|---|---|
| `compileOk` | 컴파일이 필요 없는 언어(파이썬 등)는 항상 true |
| `compileMessage` | 컴파일러 stderr (실패시 CompileMsg로 그대로 응답에 실림) |

**RunRequest** — 이미 컴파일된 프로그램을 같은 box 안에서 한 번 실행한다.
컴파일러 플래그·실행 커맨드·프로세스 제한·환경변수 같은 언어별 세부사항은 여기 없다
— Executor가 Start 때 받은 `language`로 자기 내부 `language.Languages`에서 알아서
채운다. Orchestrator는 문제(problem) 단위의 제한값만 넘긴다.

| 필드 | 설명 |
|---|---|
| `stdin` | 테스트케이스 입력 |
| `timeLimitSec` / `memoryLimitKb` | 문제별 제한 (S3 메타데이터에서 옴) |
| `outputLimitKb` | 출력 크기 제한 (기본 64MB, `--fsize`로 isolate가 자체 강제) |

**RunResponse** — isolate meta 파일을 파싱한 결과 + 실제 stdout.

| 필드 | 설명 |
|---|---|
| `status` | `"OK"`/`"RE"`/`"SG"`/`"TO"`/`"XX"` (isolate meta의 status 그대로) |
| `exitCode` / `exitSig` | 종료 코드 / 시그널 번호 |
| `timeSec` / `wallSec` / `maxRssKb` | CPU 시간 / 경과 시간 / 최대 메모리 |
| `cgOomKill` | cgroup OOM killer에 의해 죽었는지 |
| `stdout` | 실행 결과 표준출력 (판정은 전부 Orchestrator 쪽에서 함) |

## 🖥️ 서버 구현 (`executor/internal/execserver`)

- **`server.go`** — `Serve(ln, handler)`가 `Accept()` 루프를 돌며 연결마다
  `handleConn` 고루틴을 띄운다. `handleConn`은 `json.Decoder`로 프레임을 하나씩
  읽어 `handler.handleFrame`에 넘기고, 응답을 인코딩해서 돌려준 뒤 `done`이면
  연결을 닫는다. 스트림이 깨지거나(EOF, 잘못된 JSON) `done` 플래그가 서면 그 자리에서
  종료 — 연결마다 독립된 고루틴이라 한 세션이 죽어도 다른 세션에 영향 없다.
- **`handler.go`** — `Handler`가 `isolate.BoxPool`을 들고 있고, `session`
  구조체(연결 하나당 하나)가 어떤 box를 어떤 언어로 열었는지 기억한다.
  - `start()`: `language.GetLanguage`로 언어 정의를 찾고, `Pool.Acquire`로 box를
    받아 소스를 쓰고, 컴파일 커맨드가 있으면 `isolate --run`으로 컴파일한 뒤 결과를
    반환한다. 실패하면 그 자리에서 box를 반납한다.
  - `run()`: 세션에 저장된 언어의 실행 커맨드로 `isolate --run`을 한 번 실행하고,
    stdout을 읽어 응답에 실어 보낸다. Go/JVM처럼 가상주소공간을 크게 예약하는 언어는
    `--mem` 자체를 생략(`SkipVirtualMemLimit`)하고 실측 max-rss로만 판정하도록 하는
    기존 로직도 그대로 옮겨왔다.
  - box 정리(`Pool.Release`)는 `End` 프레임을 받았을 때, 그리고 세션 도중 에러가 나
    연결이 끊길 때 모두 `handleConn`의 `defer`가 보장한다 — box 반납 누락(=box 풀
    고갈)이 나지 않도록 이중으로 걸어뒀다.

## 🔗 클라이언트 구현 (`worker/internal/executorclient`)

- `Client.NewSession(ctx)`가 `net.Dialer.DialContext(ctx, "unix", socketPath)`로
  연결을 열고, `Session`이 `Start`/`Run`/`End` 각각을 "요청 인코딩 → 응답 디코딩 →
  `Error` 필드 확인" 한 번의 왕복(`roundTrip`)으로 구현한다.
- `judge.go`의 `JudgeSubmission`은 세션을 열자마자 `defer sess.End()`를 걸어,
  중간에 어떤 에러가 나도 Executor 쪽 box가 반드시 정리되도록 한다.

## ⚠️ 한계 / 후속 작업

- isolate는 Linux 전용이라 개발이 진행된 Windows 환경에서는 실제 소켓 왕복(Start→Run→
  stdout 확인)을 검증하지 못했다. Linux/실제 executor 컨테이너에서 스모크 테스트 필요.
- `judge.Handler`는 여전히 `StubHandler`(no-op)다. 실제 `Judger`를 큐 파이프라인에
  연결하는 작업은 별도 패치로 남아있다.
- 소켓 파일 권한(owner/mode) 제한은 아직 걸려있지 않다 — 필요하면 `net.Listen` 이후
  `os.Chmod`로 조여야 한다.
- `executor/Dockerfile`은 아직 이 Go 코드를 실제로 빌드해 넣는 멀티스테이지로 바뀌지
  않았다(현재는 isolate+런타임 설치만 되어 있고 바이너리 COPY는 주석 처리 상태) —
  다음 패치 후보.
