* **ADR-0016/0018** — 사람은 웹, 리소스는 CTF. CTF는 uuid만 안다.
* **ADR-0017** — uuid는 비밀이 아니다. 닿는 범위 자체를 막는다.

## #36 인스턴스 조회 내부 API — 🟡 교정함 (2026-10-28)

조회 자체는 ADR-0017 2-3가 시킨 것이라 원칙 위반이 아니다. 걸린 건 "어떻게 구현하겠다"는 열린 결정 세 개였고, 아래처럼 #36 이슈를 고쳤다.

* **① alive 판정(ADR-0009):** provisioner가 도커를 보지 않는다를 못박고, 조회는 ctf-redis registry만 읽어 답하도록(회수=기록 삭제이므로 "기록 있음+만료 전"=alive) 바꿨다.
* **② HTTP 서버 신설(ADR-0009·0015):** 부품을 늘리는 결정이라 이 이슈에서 안 정하고 ADR에서 득실을 따지도록 뺐다. 스트림 후보도 같이.
* **③ 계약을 이슈에 묻음(모듈 단위):** 방식(HTTP/스트림)은 계약이라 ADR-0017 2-3에서 먼저 확정 → 그 뒤 구현으로 순서를 나눴다.

추가로 #35로 host:port가 안정화돼 "주소 갱신" 동기가 약해졌으니, **지금 필요한지부터 판단**하는 선행 결정을 이슈 맨 앞에 넣었다.

아래는 교정 전 분석 기록이다.

**① ADR-0009 위배 가능 — "alive"를 누가 보나**

이슈는 응답에 `alive`(컨테이너가 살아 있나)를 넣겠다고 한다. 그런데 살아 있는지는 도커를 봐야 안다.
도커를 만지는 건 agent뿐이다(ADR-0009). provisioner가 `runtime.Running`을 직접 부르면 이 원칙이 깨진다.
이슈는 이걸 "정해야 한다"로 열어뒀다. **provisioner가 도커를 보지 않는다를 전제로 못박아야 한다.**
→ provisioner는 ctf-redis의 registry만 읽어 답하고(그건 ADR-0012상 가능), "살아 있나"가 꼭 필요하면 agent에 묻는 경로로 간다.

**② 부품을 늘린다 — provisioner에 HTTP 서버**

"HTTP + 짧은 캐시가 유력"이라고 한다. 그러면 provisioner에 HTTP 서버가 새로 생긴다(지금은 pprof뿐).
ADR-0009는 부품을 함부로 안 늘리는 방향이고, ADR-0015는 단일 장애점을 경계했다.
새 listener는 감시·배포·장애 포인트가 하나 느는 것이다. **추가 전에 "정말 필요한가"를 따져야 한다.**

**③ 모듈 단위 — 계약 결정을 이슈에 묻었다**

"방식(HTTP vs 스트림 vs 직접 읽기)은 이 이슈에서 결정"이라고 한다. 이건 웹↔provisioner 또는 provisioner↔agent의 **계약**이고 되돌리기 비용이 크다.
구현 이슈 안에서 결정할 게 아니라 **ADR로 먼저 드러내고 판단**해야 한다(이슈도 "2-3에 기록"이라 쓰긴 했다). 계약과 구현을 한 이슈에 섞지 않는다.

**추가로 — 정말 지금 필요한가**

내가 web 작업 정리에 적었듯, #35 이후 host는 "컨테이너 이름", port는 "EXPOSE 포트"라 **재생성해도 안 바뀐다.**
그래서 "캐시가 낡아 죽은 포트를 준다"는 원래 동기가 약해졌다. 매 요청 조회는 프록시 지연을 늘린다.
**이 이슈가 지금 필요한지부터 다시 보는 걸 권한다.** 필요하면 ②③을 정리한 ADR로 승격.

## #37 웹 연동 운영 설정 — 🟡 대체로 OK

운영 설정 문서라 원칙 위배는 아니다. ADR-0012(provisioner가 양쪽 redis)와 ADR-0009(단일 호스트)를 제대로 짚었다. 두 가지만.

* **secret 중복.** `REDIS_PASSWORD`가 웹 `.env`와 provisioner `.env` 두 곳에 산다. 지금 규모에선 감수지만, "바꿀 때 같이 바꾼다"는 사람이 놓치는 자리다. 문서에 눈에 띄게 적어둘 것.
* **한 이슈에 여러 관심사.** redis 비번 + 네트워크 이름 + 배포 순서 + 호스트. 운영 runbook이라 묶는 건 받아들일 만하지만, 실제로는 RB로 만들어 #35 runbook과 합치는 게 깔끔하다(이슈도 그렇게 적었다).

## #38 PER_USER 재사용 expiresAt — 🟢 좋은 이슈

원칙에 부합한다. 오히려 #33의 실제 빈틈을 정확히 짚었다.

* `Existing` 응답에 `expiresAt`이 비어 재사용 인스턴스가 10분짜리로 보관되던 문제. #33에서 registry에 `expiresAt`을 저장하게 됐으니 dispatcher가 채우면 된다.
* **경계를 지켰다.** `Existing` 시그니처를 안 바꾸고 dispatcher에서 채운다("만료는 handler·registry가 정하고 Existing은 떠 있나만 본다"). 역할 분리가 맞다.
* 수명을 연장하지 않는다는 것도 reaper 원칙과 맞다.

그대로 진행해도 된다. 작업량도 작다.

## #39 web 접속 이름 63자 alias — 🟢 맞는 수정, 가정 하나

DNS 라벨 63바이트 한계는 실제 버그고, alias로 푸는 방향도 맞다. 이름 규칙(= 같은 인스턴스 기준, reaper가 씀)을 안 건드리고 접속용 이름만 따로 주는 것도 원칙에 맞다. 한 가지만 확인.

* **"uuid 36자" 가정.** 이슈는 `i-{uuid}`가 38자라고 본다. 그런데 agent의 `uuidPattern`은 uuid를 **최대 63자**까지 허용한다(`handler.go`). uuid가 길면 `i-` + uuid도 63자를 넘는다.
  이슈가 "alias 63자 검증, 넘으면 FAILED"를 넣어둬서 터지진 않지만, **웹이 보내는 uuid 실제 길이**를 확인해야 한다. 늘 36자면 문제없고, 길어질 수 있으면 FAILED가 정상 요청을 막을 수 있다.

## 정리

* **#38, #39는 진행해도 된다.** #39는 uuid 길이만 확인.
* **#37은 runbook으로 합치고 secret 중복만 눈에 띄게.**
* **#36은 멈추고 다시 본다.** (1) provisioner가 도커를 안 본다 못박기, (2) HTTP 서버 추가가 정말 필요한지, (3) 계약은 ADR로 먼저. 그리고 #35로 host가 안정화돼서 애초에 지금 필요한 이슈인지부터 판단.
