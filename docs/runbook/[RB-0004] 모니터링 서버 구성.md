* **최종 수정일:** 2026-11-23

## 1. 개요 및 트리거

로그·메트릭 수집(ADR-0024)을 처음 켤 때 **한 번** 실행한다. CTF EC2를 새로 만들 때도 다시 한다.

Alloy·Loki·Prometheus·Grafana는 CTF EC2 안에서 다른 서비스와 같은 `docker-compose.prod.yml`로 뜬다.
CI가 배포하므로 서비스 자체는 손으로 띄우지 않는다. 이 절차는 그 전에 서버에 필요한 것만 준비한다.

* 모니터링 데이터를 둘 **별도 EBS 볼륨**을 붙이고 디렉터리 소유자를 맞춘다.
* `.env`에 Grafana 관리자 비밀번호를 넣는다.
* 문제 컨테이너 로그가 디스크를 채우지 않게 도커 기본 로그 설정을 건다.

> ⚠️ **순서가 중요하다.** 이 변경이 main에 들어가면 CI가 배포한다. 그 전에 단계 1~3을 끝내지 않으면
> `deploy.sh`의 사전 검사(데이터 디렉터리, `GRAFANA_ADMIN_PASSWORD`)에서 배포가 멈춘다.
> 기존 컨테이너는 그대로 돌아서 CTF는 멈추지 않지만, 배포가 실패로 끝난다. **단계 1~3을 먼저 하고 머지한다.**

## 2. 사전 준비 사항 및 리스크

* **필요 권한:** AWS 콘솔(EC2, EBS), CTF EC2 SSH(`sudo` 필요).
* **주의사항:**

  > ⚠️ 단계 1에서 **새 볼륨**을 포맷한다. 장치 이름을 잘못 고르면 다른 디스크가 지워진다. `lsblk`로 크기와
  > 마운트 상태(비어 있음)를 반드시 확인한다.

  > ⚠️ 단계 4(daemon.json)는 도커를 재시작한다. 문제 컨테이너가 같이 내려갔다 올라오고 ctf-redis가 비워진다.
  > 대회 중에는 하지 않는다.

  > ⚠️ 모니터링 컨테이너 4개가 메모리 약 1.2GB를 쓴다. EC2 타입을 정할 때 더한다(ADR-0024).

## 3. 단계별 실행 절차

### 단계 1. EBS 볼륨 생성·연결·마운트

AWS 콘솔에서:

| 항목 | 값 |
|---|---|
| 타입·크기 | gp3, 30GB (Prometheus 상한 10GB + Loki + 여유) |
| 가용 영역 | CTF EC2와 같은 AZ |
| 연결 | CTF EC2에 연결(Attach) |

CTF EC2에서 새 장치를 찾는다. Nitro 인스턴스는 `/dev/nvme1n1`처럼 보인다.

```bash
lsblk -o NAME,SIZE,TYPE,MOUNTPOINT,FSTYPE
```

**30G이고 MOUNTPOINT·FSTYPE이 비어 있는 장치**가 새 볼륨이다. 아래 `<DEV>`를 그 이름으로 바꾼다.

```bash
sudo mkfs.ext4 -L ctf-monitoring /dev/<DEV>
sudo mkdir -p /var/lib/monitoring
echo 'LABEL=ctf-monitoring /var/lib/monitoring ext4 defaults,nofail 0 2' | sudo tee -a /etc/fstab
sudo mount -a
df -h /var/lib/monitoring
```

* `LABEL=`로 적는 이유: 장치 이름은 재부팅이나 인스턴스 타입 변경 때 바뀔 수 있다.
* `nofail`: 볼륨이 떨어져 있어도 EC2가 부팅된다. 대신 그 상태면 빈 디렉터리에 쌓이니 `ctf-start.sh`가 FAIL로 알려 준다.

### 단계 2. 데이터 디렉터리와 소유자

컨테이너는 이미지 안의 사용자로 돈다. 소유자가 다르면 쓰기 권한이 없어 재시작을 반복한다.

```bash
sudo mkdir -p /var/lib/monitoring/{loki,prometheus,grafana}
sudo chown -R 10001:10001 /var/lib/monitoring/loki        # grafana/loki
sudo chown -R 65534:65534 /var/lib/monitoring/prometheus  # prom/prometheus (nobody)
sudo chown -R 472:0       /var/lib/monitoring/grafana     # grafana/grafana
```

다른 경로를 쓰려면 `.env`의 `MONITORING_DATA_DIR`를 바꾼다. 대시보드의 "모니터링 볼륨" 패널은 `/var/lib/monitoring`을 본다.

### 단계 3. .env

```bash
cd ~/ctf
cat >> .env <<'EOF'
GRAFANA_ADMIN_USER=admin
GRAFANA_ADMIN_PASSWORD=<긴 비밀번호>
MONITORING_DATA_DIR=/var/lib/monitoring
LOKI_RETENTION_PERIOD=4320h
PROMETHEUS_RETENTION=180d
PROMETHEUS_RETENTION_SIZE=10GB
EOF
```

비밀번호는 Grafana가 **처음 뜰 때만** 쓰인다. 이후 바꾸려면 Grafana UI(프로필 → 비밀번호 변경)에서 바꾼다.

이제 머지하면 CI가 배포한다. CI를 기다리지 않으려면 새 파일(compose, `alloy/`, `monitoring/`)이 배포 폴더에 있는 상태에서 같은 태그로 다시 배포한다.

```bash
./deploy.sh "$(grep '^current=' .deploy_state | cut -d= -f2)"
```

### 단계 4. 도커 기본 로그 설정 (문제 컨테이너용)

compose의 `logging` 설정은 compose가 만든 컨테이너에만 걸린다. agent가 띄우는 문제 컨테이너는 도커 기본값
(무제한 json-file)을 따른다. 출력을 쏟는 문제 하나가 디스크를 채울 수 있다. **대회 전에**:

```bash
sudo cat /etc/docker/daemon.json   # 있으면 내용을 합친다. runsc(gVisor) 설정이 있을 수 있다
```

`log-driver`, `log-opts`를 넣는다:

```json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
```

```bash
sudo systemctl restart docker
~/ctf/ctf-start.sh
```

이미 떠 있던 컨테이너에는 적용되지 않는다. 새로 만들어지는 컨테이너부터 적용된다.

## 4. 확인

### Grafana 접속

```bash
ssh -L 3000:127.0.0.1:3000 ubuntu@<CTF EC2 공인 IP>
```

브라우저에서 `http://localhost:3000`으로 접속한다. `.env`의 관리자 계정으로 로그인하고 **Dashboards → Nimda CTF → CTF 서버 개요**를 연다.

* 개요의 CPU·메모리·디스크·모니터링 볼륨에 값이 있다 → 호스트 메트릭, 볼륨 마운트 OK
* 컨테이너 패널에 `ctf-agent`, `ctf-provisioner` 같은 **이름**이 보인다 → cAdvisor와 이름 대응표 OK
* ctf-redis 패널에 `ctf:agent:ops` 스트림이 있다 → redis 메트릭 OK(스트림은 첫 요청 뒤에 생긴다)
* 서비스 로그에 agent·provisioner 줄이 있다 → 로그 OK

`ctf-start.sh`의 점검에도 모니터링 컨테이너 4개와 "모니터링 볼륨" 줄이 나온다.

### Alloy 파이프라인 상태

```bash
docker logs --tail 50 ctf-alloy
ssh -L 12345:127.0.0.1:12345 ubuntu@<CTF EC2 공인 IP>   # 로컬 브라우저에서 http://localhost:12345
```

## 5. 백업과 지난 기록 보기

* **지난 기록 보기:** EC2를 켜고 SSH 터널로 Grafana에 접속해 시간 범위를 그 대회 날짜로 바꾼다.
  EC2를 켜면 CTF 컨테이너도 같이 뜬다(restart 정책).
* **백업:** 대회가 끝나면 EBS 콘솔에서 `ctf-monitoring` 볼륨의 스냅샷을 뜬다. 정기적으로 하려면 Data Lifecycle Manager로 자동화한다.
  스냅샷에는 로그 전체가 들어 있으니 공유 권한을 열지 않는다.
* **EC2를 새로 만들 때:** 볼륨을 옛 인스턴스에서 떼어(Detach) 새 인스턴스에 붙이고, 단계 1의 fstab 줄만 다시 넣는다(포맷하지 않는다).

## 6. 문제 해결

| 증상 | 원인 | 조치 |
|---|---|---|
| `deploy.sh`가 `/var/lib/monitoring/loki 가 없습니다`로 멈춤 | 단계 2를 안 함 | 단계 2 후 다시 배포 |
| `deploy.sh`가 `GRAFANA_ADMIN_PASSWORD must be set`로 멈춤 | 단계 3을 안 함 | `.env`에 넣고 다시 배포 |
| `deploy.sh`에 "별도 볼륨이 아닙니다" 경고 | 볼륨이 마운트되지 않음 | `sudo mount -a`, `lsblk`로 확인. 콘솔에서 볼륨이 연결돼 있는지 본다 |
| `ctf-loki`·`ctf-prometheus`·`ctf-grafana`가 재시작 반복, 로그에 `permission denied` | 디렉터리 소유자 | 단계 2의 `chown` |
| 지난 대회 기록이 안 보임 | 볼륨이 안 붙은 채 켜져 빈 디렉터리에 쌓임, 또는 보관 기간 지남 | 볼륨 마운트 확인. 보관 기간(`LOKI_RETENTION_PERIOD`, `PROMETHEUS_RETENTION`)을 확인 |
| 로그는 오는데 컨테이너 이름이 비어 있음 | docker-proxy가 응답하지 않음 | `docker logs ctf-docker-proxy`에서 403/503을 본다 |
| docker-proxy 로그에 403 | 허용하지 않은 Docker API 호출 | Alloy 설정에 새 컴포넌트를 넣었다면 프록시 환경변수(CONTAINERS·NETWORKS·INFO)를 확인. 아니면 누가 불렀는지 조사 |
| 문제 컨테이너 로그가 중간중간 빠짐 | 의도한 동작. 초당 20줄 제한 | 제한은 `deploy/alloy/config.alloy`의 `stage.limit` |
| 모니터링 볼륨이 참 | Loki는 크기로 지우지 않는다 | `LOKI_RETENTION_PERIOD`·`PROMETHEUS_RETENTION_SIZE`를 줄이거나 EBS 볼륨을 늘리고 `sudo resize2fs /dev/<DEV>` |

## 7. 설정을 바꿀 때

* **수집 설정**(`deploy/alloy/config.alloy`), **Loki·Prometheus 설정**(`deploy/monitoring/`): PR로 바꾼다. CI가 Alloy 문법을 검사하고, 배포 때 alloy·loki·prometheus를 재시작한다.
* **대시보드**: Grafana에서 고쳐도 저장되지 않는다(파일 프로비저닝). 고친 뒤 **Export → JSON**으로 받아
  `deploy/monitoring/grafana/dashboards/ctf-overview.json`을 바꾸고 PR로 올린다. 배포 후 30초 안에 다시 읽는다.
* **보관 기간**: `.env` 값을 바꾸고 같은 태그로 다시 배포한다.
